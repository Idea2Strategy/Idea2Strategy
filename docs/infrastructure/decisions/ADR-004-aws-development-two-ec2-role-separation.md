# ADR-004: Development EC2 2대 역할 분리

- 상태: Proposed
- 작성일: 2026-07-29
- 결정자: 인프라 담당자
- 관련 질문: INFRA-Q-001, INFRA-Q-003, INFRA-Q-008, INFRA-Q-010, INFRA-Q-015
- 관련 정본 ID: technology.need.server-runtime, quality.failure-safety, quality.reproducibility
- Supersedes: ADR-003 (이 ADR이 Accepted가 될 때)

## 맥락

기존 `ADR-003`은 애플리케이션·작업자·Caddy·Redis를 단일 EC2의 Docker Compose에서 실행하는 방향을 제안했다. 이후 백테스트와 배치 처리가 CPU·메모리를 오래 점유해 실시간 모의투자 API·WebSocket·주문 처리에 영향을 줄 가능성을 줄이기 위해 실행 자원을 역할별로 먼저 분리하는 방향이 제시되었다.

Spring 코드는 일반 Backend, Batch, Backtest의 독립 컴파일·실행 단위 3개로 나눈다. 이 ADR은 각 실행 단위를 EC2 역할 경계에 배치하며, 공용 DB와 Repository 구조는 `ADR-005`에서 별도로 제안한다.

## 선택지

### 선택지 A: 단일 EC2 유지

- 장점: 배포와 내부 통신이 가장 단순하고 비용이 낮다.
- 단점: 백테스트·배치 부하가 실시간 모의투자 서비스와 자원을 경쟁하며 한 인스턴스 장애가 전체 기능을 중단시킨다.

### 선택지 B: EC2 2대를 역할별로 분리

- 장점: 계산 부하와 사용자 요청 처리를 격리하고 역할별로 사양·가동 시간·배포를 독립 조정할 수 있다.
- 단점: 네트워크·IAM·배포 대상·관측 지점이 늘고 Redis와 작업 전달 경계를 추가로 결정해야 한다.

### 선택지 C: Spring과 Worker를 여러 서비스로 세분화

- 장점: 기능별 독립 배포와 확장에 유리하다.
- 단점: 현재 개발 단계에서는 서비스 계약·장애 처리·분산 운영 복잡도가 과도하며 Spring 분리 기준도 아직 없다.

## 제안

선택지 B를 우선안으로 기록한다.

- 백테스트·배치 EC2는 백테스트 실행과 배치성 데이터 처리를 담당한다.
- 모의투자 서비스 EC2는 사용자 요청, API·WebSocket과 실시간 모의투자 처리를 담당한다.
- 일반 Backend Spring은 모의투자 서비스 EC2에 배치한다.
- Batch Spring과 Backtest Spring은 백테스트·배치 EC2에 배치한다.
- 각 EC2는 독립적인 Docker Compose 배포 단위, 인스턴스 역할과 보안 그룹을 사용한다.
- 외부 80·443 트래픽은 모의투자 서비스 EC2의 Caddy로만 받는다.
- 백테스트·배치 EC2는 공개 인바운드를 두지 않고 SSM으로 운영한다.
- RDS PostgreSQL과 S3의 기존 저장 책임은 유지하며 두 EC2에 최소 권한으로 접근을 허용한다.
- 백테스트 요청은 일반 Backend Spring에서 Backtest Spring의 비공개 HTTP API로 전달한다.
- Backtest Spring의 내부 포트는 인터넷에 공개하지 않고 모의투자 서비스 EC2 보안 그룹에서 오는 트래픽만 허용한다.
- 초기에는 SQS를 두지 않으며 처리량·재시도·장애 격리 필요가 측정되면 같은 요청 경계 뒤에 추가한다.
- Backtest Spring은 접수한 요청을 RDS에 `QUEUED`로 보존하고 초기에는 최대 한 건씩 실행한다.
- 작업 선점은 `FOR UPDATE SKIP LOCKED`를 사용해 향후 실행기를 늘려도 중복 실행을 막고, 계산 중에는 DB 잠금을 유지하지 않는다.
- `RUNNING` 작업의 생존 신호가 만료되면 처음부터 자동 재실행하며 최대 1회만 허용한다.
- 생존 신호는 30초마다 기록하고 마지막 갱신 후 3분이 지나면 중단으로 판단한다.
- 자동 재실행 횟수는 `attempt_count`, 결과 쓰기 유효성은 `execution_generation`으로 관리한다.
- 두 번째 실패는 `FAILED`로 종료하고 이전 세대 실행기의 늦은 RDS·S3 결과 확정을 차단한다.
- 실시간 Market Data Worker와 Redis는 모의투자 서비스 EC2에 배치한다.
- 과거 Market Data Worker와 Parquet 생성·검증·재가공은 백테스트·배치 EC2에 배치한다.
- 두 EC2의 대량 시장 데이터 공유는 S3 불변 객체와 RDS 매니페스트를 통하며 백테스트·배치 EC2는 Redis에 접근하지 않는다.

## 결과와 영향

- 기대 효과: 백테스트·배치의 자원 사용이 실시간 모의투자 응답성과 직접 경쟁하는 위험을 줄인다.
- 비용 영향: EC2·EBS·관측 비용이 인스턴스 1대분 증가한다. 역할별로 사양과 가동 시간을 다르게 적용해 조정할 수 있다.
- 보안 영향: RDS와 S3 접근 권한을 EC2 역할별로 분리하고, 배치 EC2에는 외부 진입점을 만들지 않는다.
- 배포 영향: GitHub Actions와 SSM 배포가 역할별 Compose 대상과 이미지 조합을 구분해야 한다.
- 관측 영향: 실시간 서비스 지표와 백테스트·배치 처리량·대기 시간·실패율을 인스턴스별로 구분한다.
- 장애 영향: 한 역할의 장애가 다른 역할의 프로세스를 직접 종료시키지는 않지만, 공유 RDS·S3와 추후 선택할 Redis·작업 전달 경로는 공통 장애 지점이 될 수 있다.

## 롤백

비용이나 운영 복잡도가 현재 규모에 비해 크다고 판단되면 동일한 컨테이너 이미지를 단일 EC2 Compose 조합으로 다시 배포한다. 영속 상태는 RDS와 S3에 두므로 EC2 통합 시 로컬 디스크 데이터를 이관 경로로 사용하지 않는다.
