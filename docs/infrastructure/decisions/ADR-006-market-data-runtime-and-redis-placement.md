# ADR-006: 시장 데이터 실행 경계와 Redis 배치

- 상태: Proposed
- 작성일: 2026-07-29
- 결정자: 인프라 담당자
- 관련 질문: INFRA-Q-005, INFRA-Q-007, INFRA-Q-008, INFRA-Q-015, INFRA-Q-017
- 관련 정본 ID: decision.data.hybrid, technology.need.market-data, technology.need.object-storage, technology.need.server-runtime
- Supersedes:

## 맥락

실시간 시장 데이터는 모의투자 주문·체결 판단과 사용자 가격·차트에 사용되므로 낮은 지연과 지속적인 연결이 중요하다. 반면 과거 데이터 수집, 10년 백필, 정규장 필터링, Parquet 압축과 봉 집계는 CPU·메모리·디스크 사용량이 크지만 사용자 요청 경로와 같은 지연 수준을 요구하지 않는다.

Development 실행 환경은 모의투자 서비스 EC2와 백테스트·배치 EC2로 분리하기로 했다. 시장 데이터 실행 단위를 잘못 배치하면 과거 데이터 작업이 실시간 주문 처리에 영향을 주거나, 백테스트 EC2를 비용 절감을 위해 중지하지 못할 수 있다.

## 선택지

### 선택지 A: 실시간과 과거 처리를 역할별 EC2에 분리

- 실시간 Worker와 Redis는 모의투자 서비스 EC2에 둔다.
- 과거 Worker와 Parquet 재가공은 백테스트·배치 EC2에 둔다.
- 대량 데이터 공유는 S3 객체와 RDS 매니페스트로 제한한다.

### 선택지 B: 모든 Market Data Worker를 백테스트·배치 EC2에 배치

- 시장 데이터 실행 위치는 단순해진다.
- 실시간 데이터가 EC2 사이를 거쳐 Redis에 도달하고, 배치 부하와 장애가 실시간 모의투자에 영향을 준다.
- 백테스트·배치 EC2를 장중에 중지할 수 없다.

### 선택지 C: 모든 Market Data Worker를 모의투자 서비스 EC2에 배치

- 실시간 Worker와 Redis 통신은 단순하다.
- 과거 백필과 Parquet 압축이 API·WebSocket·모의투자와 CPU·메모리를 경쟁해 EC2 역할 분리의 효과가 줄어든다.

## 결정

인프라 담당자는 선택지 A를 선택했다. 팀 합의와 실제 부하 검증 전까지 이 ADR은 `Proposed`로 유지한다.

### 모의투자 서비스 EC2

- Caddy, Frontend, `backend-app`
- 실시간 Market Data Worker
- Redis
- 실시간 스트림 수신·기본 검증
- 실시간 가격·차트 Hot Projection 갱신
- 실시간 원본 청크의 S3 업로드

Redis는 같은 EC2의 Docker 네트워크에서만 접근하게 하고 인터넷과 백테스트·배치 EC2에 포트를 공개하지 않는다. Redis 데이터는 공식 상태가 아니며 RDS·S3와 실시간 공급자 입력으로 재구축할 수 있어야 한다.

### 백테스트·배치 EC2

- `batch-app`, `backtest-app`
- 과거 Market Data Worker
- Alpaca 과거 데이터 수집과 검증
- 정규장 필터링, 정렬·중복 제거
- Parquet 생성·봉 집계·압축·재가공

백테스트·배치 EC2는 Redis를 읽지 않는다. 백테스트 입력은 S3의 검증된 불변 객체와 RDS의 데이터셋·객체 매니페스트를 기준으로 한다.

## 데이터 저장 경계

- 실시간 Worker는 원본을 짧게 버퍼링한 뒤 시간 구간과 세대별 임시 S3 객체로 업로드한다.
- 검증이 끝난 S3 객체만 RDS의 매니페스트·해시·계보에 연결한다.
- 과거 Worker와 Parquet 배치 처리는 기존 객체를 덮어쓰지 않고 새 불변 객체와 리비전을 발행한다.
- 두 EC2는 대량 시장 데이터 본문을 직접 전송하지 않고 S3를 교환 경계로 사용한다.
- 정확한 버퍼 크기, 청크 시간, 객체 prefix와 매니페스트 소유권은 구현 전에 별도로 확정한다.

## 결과와 영향

- 기대 효과: 과거 데이터 처리 부하를 API·WebSocket·실시간 모의투자에서 격리한다.
- 지연 효과: 실시간 Worker와 Redis가 같은 호스트에 있어 EC2 간 홉이 없다.
- 비용 효과: 기존 EC2 2대 안에서 역할을 배치하므로 즉시 서버가 추가되지는 않는다.
- 자원 위험: 서비스 EC2의 Spring·Redis·실시간 Worker가 2GiB 메모리에서 경쟁할 수 있으므로 메모리·OOM·처리 지연을 측정해야 한다.
- 장애 영향: 서비스 EC2 장애 시 실시간 수집·가격·차트·모의투자가 함께 중단되지만 과거 처리와 백테스트는 계속할 수 있다.
- 보안 영향: 실시간 공급자 자격 증명과 실시간 S3 prefix 권한은 서비스 EC2 역할에만, 과거·파생 prefix 권한은 배치 EC2 역할에 최소 권한으로 부여한다.

## 확장과 롤백

실시간 처리 지연, 지속적인 메모리 부족 또는 모의투자와의 자원 경쟁이 측정되면 실시간 Worker를 세 번째 EC2로 옮긴다. 이때 여러 서비스가 Redis를 공유해야 하면 ElastiCache를 재검토한다. 반대로 운영 복잡도가 과도하면 동일 Worker 이미지를 하나의 EC2 Compose 프로필로 합칠 수 있다. 영속 데이터는 RDS와 S3에 있으므로 EC2 이동 시 로컬 디스크를 이관 기준으로 사용하지 않는다.
