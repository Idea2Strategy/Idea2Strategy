# ADR-005: Spring 실행 모듈 분리와 공용 RDS·CQRS-lite

- 상태: Proposed
- 작성일: 2026-07-29
- 결정자: 인프라 담당자
- 관련 질문: INFRA-Q-004, INFRA-Q-008, INFRA-Q-010, INFRA-Q-015, INFRA-Q-016
- 관련 정본 ID: technology.need.server-runtime, technology.need.logical-data-model, quality.auditability, quality.reproducibility
- Supersedes:

## 맥락

백테스트·배치 처리와 실시간 모의투자 서비스를 EC2 역할별로 분리하려면 Backend 코드도 독립적으로 빌드하고 배포할 수 있어야 한다. 다만 사용자·전략·봇·주문·체결·백테스트 상태와 결과 관계는 공용 RDS PostgreSQL에 저장되어 세 실행 단위가 같은 스키마에 접근해야 한다.

단순한 Java 패키지 분리는 하나의 실행 파일과 배포 수명주기를 유지하므로 이 요구를 충족하지 않는다. 반대로 초기부터 저장소와 데이터베이스를 서비스별로 완전히 분리하면 현재 규모에 비해 계약·분산 트랜잭션·운영 부담이 커진다.

## 선택지

### 선택지 A: Backend 저장소의 Gradle 멀티 모듈

- 일반 Backend, Batch, Backtest를 각각 실행 가능한 Spring Boot 모듈로 만든다.
- 공용 DB·Flyway·값 타입 등 최소 기술 코드를 라이브러리 모듈로 공유한다.
- 각 실행 모듈을 별도로 컴파일·테스트·이미지화할 수 있다.

### 선택지 B: Spring 애플리케이션마다 별도 저장소

- 배포와 소유권은 가장 강하게 분리된다.
- 공용 DB 계약과 공용 코드의 버전 배포·호환 관리가 추가로 필요하다.

### 선택지 C: 단일 Spring 애플리케이션의 패키지 분리

- 코드 탐색과 초기 개발은 단순하다.
- 독립 컴파일·이미지·EC2 배포와 장애 격리 요구를 충족하지 못한다.

## 제안

현재는 선택지 A를 우선안으로 기록한다.

- `backend-app`: 일반 API·WebSocket·모의투자 업무를 담당하는 실행 모듈
- `batch-app`: 정기·대량 배치를 담당하는 실행 모듈
- `backtest-app`: 백테스트 실행과 계산을 담당하는 실행 모듈
- `database-common` 또는 동등한 공용 모듈: Flyway Migration, DB 연결 설정과 공통 값 타입 등 실제로 공유가 필요한 최소 코드

세 실행 모듈은 각각 독립적으로 컴파일·테스트하고 Docker 이미지를 만든다. 일반 Backend 이미지는 모의투자 서비스 EC2에, Batch와 Backtest 이미지는 백테스트·배치 EC2에 배포한다.

## 공용 RDS 원칙

- 세 Spring 애플리케이션은 같은 RDS PostgreSQL 인스턴스와 논리 스키마를 사용한다.
- 하나의 Flyway Migration 이력과 스키마 버전을 공유한다.
- 공용 DB 사용과 모든 테이블에 대한 무제한 쓰기 권한을 동일하게 보지 않는다.
- 테이블별 쓰기 소유자와 다른 모듈의 읽기 전용 접근을 명시한다.
- 실행 애플리케이션별 PostgreSQL 계정을 분리하고 최소 권한을 적용한다.
- 애플리케이션 실행 계정에는 DDL 권한을 주지 않고, 별도 Flyway 전용 계정에만 스키마 생성·변경 권한을 부여한다.
- 여러 실행 모듈이 같은 행을 수정할 수 있다면 낙관적 잠금, 중복 실행 방지, 재시도와 멱등성 규칙이 필요하다.

### 확정된 쓰기 소유권

2026-07-29 인프라 담당자가 역할별 쓰기 소유권 분리안을 확정했다.

| 쓰기 소유 모듈 | 쓰기를 소유하는 데이터 | 다른 모듈 |
|---|---|---|
| `backend-app` | 사용자·전략·봇·주문·체결·원장 | 필요한 범위에서 조회만 허용 |
| `batch-app` | 배치 실행 상태·집계·파생 데이터 | 필요한 범위에서 조회만 허용 |
| `backtest-app` | 백테스트 실행·거래·포지션·성과 결과 | 필요한 범위에서 조회만 허용 |

다른 모듈 소유 데이터를 변경해야 하면 해당 쓰기 소유 모듈을 통해 변경한다. 구현 단계에서는 테이블·Repository·DB 권한을 이 소유권 표에 맞춰 연결한다.

### 확정된 DB 계정과 권한 분리

2026-07-29 인프라 담당자가 실행 모듈별 DB 계정 분리안을 확정했다.

| DB 계정 역할 | 쓰기 권한 | 읽기 권한 | DDL 권한 |
|---|---|---|---|
| `backend-app` 실행 계정 | Backend 소유 테이블 | 업무상 필요한 테이블 | 없음 |
| `batch-app` 실행 계정 | Batch 소유 테이블 | 업무상 필요한 테이블 | 없음 |
| `backtest-app` 실행 계정 | Backtest 소유 테이블 | 업무상 필요한 테이블 | 없음 |
| Flyway 전용 계정 | Migration에 필요한 범위 | Migration 검증에 필요한 범위 | 있음 |

- 각 실행 계정은 소유 테이블에 필요한 `INSERT`·`UPDATE`·`DELETE` 권한만 갖는다.
- 다른 모듈 소유 테이블에는 업무상 필요한 `SELECT`만 허용한다.
- Flyway 전용 계정은 애플리케이션의 상시 실행 계정으로 사용하지 않는다.
- 자격 증명은 AWS Systems Manager Parameter Store `SecureString`의 역할별 경로에 분리한다.
- 실제 계정명과 테이블별 `GRANT` 목록은 정본 DBML의 소유권 매핑 이후 확정한다.

### 확정된 Development Flyway 실행 방식

2026-07-29 인프라 담당자가 전용 배포 작업 방식을 확정했다.

1. 루트 GitHub Actions에서 테스트·이미지 빌드와 Flyway 검증을 수행한다.
2. 인프라 담당자가 검증 완료 배포 조합을 선택해 Development 배포를 시작한다.
3. GitHub Actions가 SSM Run Command로 모의투자 서비스 EC2에서 Flyway 전용 일회성 작업을 한 번 실행한다.
4. Flyway `validate`와 `migrate`가 성공한 경우에만 역할별 EC2의 Spring 애플리케이션 이미지를 갱신한다.
5. Flyway가 실패하면 애플리케이션 배포를 중단하고 원인을 수정한 새 Migration으로 다시 검증한다.

세 Spring 애플리케이션은 시작 시 Flyway Migration을 자동 실행하지 않는다. 이로써 두 EC2와 여러 Spring 프로세스가 동시에 같은 스키마를 변경하는 경로를 차단한다. Production의 실행 위치와 별도 승인 절차는 Production 구축 전에 확정한다.

### 확정된 백테스트 요청 경계

2026-07-29 인프라 담당자가 비공개 HTTP API 방식을 확정했다.

1. `backend-app`이 요청 ID와 백테스트 입력을 `backtest-app`의 비공개 HTTP API로 전달한다.
2. `backtest-app`은 요청 ID를 멱등성 키로 확인하고 자신의 DB 계정으로 실행 레코드를 생성한다.
3. `backtest-app`이 실행 상태와 결과를 RDS·S3에 기록한다.
4. `backend-app`은 필요한 상태와 결과를 조회해 사용자에게 제공한다.

`backend-app`은 백테스트 소유 테이블을 직접 변경하지 않는다. 비공개 API는 두 EC2 사이에서만 접근할 수 있으며 인터넷에 노출하지 않는다. 초기에는 SQS나 별도 메시지 브로커를 사용하지 않고, 대기량·재시도·장애 격리가 실제 병목이 될 때 API 뒤의 전달 구현을 큐로 교체한다.

### 확정된 백테스트 대기열과 동시 실행

- `backtest-app`은 접수한 실행을 RDS에 `QUEUED`로 저장한다.
- 초기 최대 동시 실행 수는 `1`이며 배포 환경 설정으로 조정할 수 있게 한다.
- 내부 실행기는 짧은 트랜잭션에서 `FOR UPDATE SKIP LOCKED`로 대기 작업을 하나 선택하고 `RUNNING`으로 변경한다.
- 상태 변경을 커밋한 뒤 DB 잠금을 해제하고 계산을 시작하므로 장시간 계산 중에 행 잠금을 유지하지 않는다.
- 향후 실행 프로세스나 EC2를 늘려도 같은 선점 규칙을 사용한다.

RDS 대기열은 현재 규모에서 별도 메시지 인프라 없이 대기 작업을 보존하기 위한 선택이다. 대기 시간, DB 폴링 부하 또는 장애 격리 요구가 기준을 넘으면 SQS로 교체한다.

### 확정된 중단 감지와 자동 재실행

- 실행기는 `RUNNING` 작업의 `last_heartbeat_at`을 30초마다 갱신한다.
- 마지막 갱신 후 3분이 지난 경우에만 실행기가 중단된 것으로 판단한다.
- 갱신 주기와 만료 시간은 배포 환경 설정으로 관리해 운영 측정 후 변경할 수 있게 한다.
- 최초 실행의 `attempt_count`는 `0`이며, 생존 신호 만료 후 자동 재실행할 때 `1`로 증가시킨다.
- 자동 재실행은 처음부터 수행하며 최대 1회만 허용한다.
- 자동 재실행된 작업이 다시 중단되거나 실패하면 `FAILED`로 종료한다.
- 입력 검증, 전략 계산 또는 데이터 오류처럼 동일 입력에서 반복될 가능성이 높은 실패는 자동 재실행하지 않는다.

각 실행 시도에는 증가하는 `execution_generation`을 부여한다. 상태와 결과를 저장하는 RDS 갱신은 작업 ID와 현재 세대가 모두 일치할 때만 성공한다. S3 상세 결과는 세대별 임시 경로에 기록하고 현재 세대가 성공한 경우에만 그 객체 매니페스트를 공식 결과로 연결한다. 이전 실행기가 늦게 살아나더라도 오래된 세대의 RDS·S3 결과는 최신 결과를 덮어쓸 수 없다.

## CQRS-lite Repository 원칙

- Command Repository는 생성·수정·삭제와 도메인 불변식이 필요한 상태 변경 경로를 담당한다.
- Query Repository는 화면, 리포트, 집계와 조회 최적화 경로를 담당한다.
- Command와 Query는 코드 인터페이스와 구현 책임을 분리하지만 초기에는 같은 PostgreSQL을 사용한다.
- 별도 Read DB, 이벤트 소싱, 메시지 브로커와 완전한 CQRS는 측정된 필요가 생기기 전에는 도입하지 않는다.
- CQRS-lite는 테이블 쓰기 소유권이나 애플리케이션 간 트랜잭션 문제를 자동으로 해결하지 않는다.

## 결과와 영향

- 기대 효과: 세 워크로드를 독립 빌드·배포하면서 DB 관계와 초기 운영 단순성을 유지한다.
- 결합 위험: 공용 스키마 변경이 세 애플리케이션에 동시에 영향을 줄 수 있다.
- 배포 영향: Flyway 변경은 세 실행 모듈의 호환성 검증 후 한 번만 적용해야 한다.
- 테스트 영향: 모듈별 단위 테스트 외에 동일 RDS 스키마를 사용하는 통합 테스트가 필요하다.
- 장애 영향: 애플리케이션 프로세스는 분리되지만 RDS는 공통 장애 지점이다.
