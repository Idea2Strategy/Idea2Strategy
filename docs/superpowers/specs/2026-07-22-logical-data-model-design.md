# Idea2Strategy 논리 데이터 모델 설계

## 상태와 범위

이 문서는 `db/schema.dbml`을 작성하기 전에 승인받을 논리 설계다. 제품 구현, DBMS 선택, ORM, 마이그레이션, 물리 파티션·샤딩·복제·배포 구조는 다루지 않는다.

논리 모델의 목적은 확정된 제품 정책을 다음 형태로 검증 가능하게 표현하는 것이다.

- 도메인별 정본 소유권과 접근 경계
- 변경 가능한 현재 상태와 추가만 가능한 불변 기록의 구분
- 잠긴 전략 버전부터 봇·주문·체결·복식 원장·성과까지의 추적 관계
- 시장 데이터와 대용량 증거 객체의 명세·버전·무결성·계보
- 백테스트와 라이브 운영, 개인 봇과 방 평가 구간의 분리
- 취소·정정·무효화를 원본 수정이 아닌 새 기록으로 표현하는 관계

## 정본 파일

- Git의 유일한 논리 데이터 모델 정본은 `db/schema.dbml`이다.
- 설명과 검토 근거는 이 설계 문서와 관련 `specs/`·`contracts/`에 둔다.
- dbdiagram 또는 다른 시각화 도구의 사본과 내보낸 이미지·SQL은 제안 또는 파생 산출물이며 정본이 아니다.
- `db/schema.dbml`은 하나의 파일로 유지하면서 DBML의 schema-qualified 테이블 이름으로 도메인을 분리한다.
- 파일이 커지더라도 도구 지원과 참조 무결성 검증 없이 여러 DBML 정본으로 나누지 않는다. 물리 DB 분리도 schema 구분만으로 미리 확정하지 않는다.

## 논리 schema 경계

### `identity`

일반 사용자 신원, 로그인 수단, 확인 이메일, 동의, 복구 수단과 세션을 소유한다.

- 서비스 도메인에는 의미 없는 내부 계정 식별자만 공개한다.
- 비밀번호·복구 코드·외부 인증 비밀의 원문은 모델에 두지 않는다.
- 관리자 신원은 일반 사용자 신원과 종류·인증 정책·권한 관계를 분리한다.

### `strategy`

전략 작업본, 공식 검증, 잠긴 출시 버전, 재사용 컴포넌트, 언어·스키마·카탈로그 버전과 종목 선택을 소유한다.

- 작업본은 현재 문서만 변경 가능하고 과거 리비전을 만들지 않는다.
- 전략 문서는 주 RDB의 구조화된 JSON 계열 문서 값으로 보관하고, 별도 NoSQL 정본은 현재 도입하지 않는다.
- 실행 의미 문서에는 타입 지정 블록·노드·포트·연결·매개변수·의미 있는 그룹과 정책을, 편집 표현 문서에는 좌표·크기·화면 이동·배율·접힘 상태처럼 실행에 영향을 주지 않는 정보를 둔다.
- 실행 의미와 편집 표현은 각각 해시를 가지며 함께 원자적으로 저장한다. 출시 버전은 둘 다 잠그되 봇 실행·백테스트 동일성은 실행 의미 해시를 기준으로 한다.
- 잠긴 버전과 컴포넌트 버전은 수정·삭제하지 않는다.
- Basic과 Pro는 같은 타입 언어 의미를 사용하되 문서 모드와 검증 규칙을 구분한다.
- Basic→Pro 변환과 구버전 변환은 원본을 바꾸지 않고 새 작업본과 출처 관계를 만든다.

### `bot`

봇 객체, 잠긴 봇 구성, 포함 전략과 예산 정책, 현재 수명주기 상태, 방 소속 여부와 봇별 공식 사건 순서를 소유한다.

- 봇은 출시 후 구성을 수정하지 않는다.
- 각 봇은 `1`부터 증가하는 독립적인 공식 사건 순번을 가진다.
- 현재 상태는 조회 가능한 행으로 유지하되 상태 전이 사건은 불변 기록으로 남긴다.
- 실행·중단만 존재하며 중단된 봇은 다시 실행하지 않는다.

### `trading`

주문 후보 확정 결과, 공식 주문, 취소·교체 관계, 개별 체결, 자금 예약, 복식 원장, 전략 귀속, 체결 묶음과 포지션 파생 근거를 소유한다.

- 주문·체결·원장 거래·원장 항목·체결 묶음은 불변 기록이다.
- 원장 거래의 항목 합계는 균형을 이루어야 한다.
- 정정은 원본을 참조하는 반대 거래와 필요한 대체 거래로 표현한다.
- 미체결 주문 예약은 실제 체결 회계와 분리하고 활성 예약의 중복 사용을 막는다.
- 전략 귀속 합계는 봇 전체 공식 체결·원장 결과와 조정 가능해야 한다.
- 롱 매도와 숏 상환의 체결 묶음 소비는 전략 귀속 안에서 FIFO를 사용한다.

### `market_data`

지원 종목, 공급자·피드, 원천·조정·파생 데이터셋 명세, 개정본, 데이터 처리 실행, 품질 상태, 기업행사와 저장 객체 계보를 소유한다.

- 대용량 분봉 본문을 주 RDB 테이블에 직접 저장하지 않는다.
- 관계형 정본은 데이터셋 기간·계층·개정·처리 버전·행 수·해시·객체 식별자와 기반/파생 관계를 가진 manifest다.
- raw와 adjusted를 구분하고 기존 개정본을 덮어쓰지 않는다.
- 저장 객체가 없거나 해시가 다르면 다른 최신 데이터로 대체하지 않는다.

### `backtest`

분기별 공식 평가 기간, 출시 버전당 하나인 자동 실행, 잠긴 입력 데이터 버전 묶음, 실행 상태, 월별 판단 요약, 거래 상세와 성과 계산 입력·결과를 소유한다.

- 라이브 봇 사건·원장·잔액과 데이터를 공유하지 않는다.
- 하나의 출시 전략 버전에는 최대 하나의 공식 자동 실행만 연결한다.
- RDB는 실행·잠긴 입력·월별 판단 요약·조회용 성과 요약·실패 사유와 상세 객체 manifest를 소유한다.
- 주문·체결·취소·거절·비용·거래 후 잔액·포지션·재생 원장·성과 계산 시계열의 대량 상세 정본은 실행·ET 월·기록 종류별 불변 객체로 저장하고 주 RDB에 행 단위로 직접 적재하지 않는다.
- 월별 판단 요약, 객체 저장 거래 상세, 성과 데이터는 서로 다른 정본 관계로 유지하되 같은 실행과 전략 스냅샷에 연결한다.
- manifest는 객체 논리 식별자·기간·종류·형식·스키마 버전·행 수·크기·내용 해시·계보를 보존하며, 객체 누락이나 해시 불일치 시 다른 최신 객체로 대체하지 않는다.
- 실패·백테스트 불가 결과를 성공이나 부분 성과로 표현하지 않는다.

### `competition`

방, 잠긴 일정·규칙, 참여 봇, 익명 별칭, 공개 자격, 점수 템플릿 스냅샷, 평가 구간과 최종 순위·무효화 관계를 소유한다.

- 사용자가 아니라 봇만 비교한다.
- 같은 전략에서 생성해도 방 참여 봇은 독립된 봇 객체다.
- 점수 규칙과 방 규칙은 모집 시작 뒤 변경하지 않는다.
- 성과 계산용 가상 청산은 실제 `trading` 주문·현금·포지션·원장을 변경하지 않는다.
- 방 종료 뒤 계속 실행하는 동일 봇은 실제 상태를 이어가되 방 평가 구간은 종료 시점에 고정한다.

### `operations`

필수·선택 알림, 구조화된 문의·신고·이의제기, 관리자 역할·권한·위임, 고영향 작업, 감사 사건, 불변 증거 객체 참조와 후속 전달 작업을 소유한다.

- 사람인 운영자는 사용자의 상세 전략 원문을 읽을 수 없다.
- 권한 변경과 고영향 작업은 수행자·권한·대상·근거·전후 결과를 불변 감사 기록으로 남긴다.
- 알림 전달 실패는 공식 주문·체결·원장 결과를 바꾸지 않는다.
- 대용량 계산 추적과 입력 스냅샷은 객체 저장소에 두고 내용 해시와 계보로 연결한다.

## DBML 표현 규칙

DBML에는 schema-qualified 이름을 사용한다.

```dbml
Project Idea2Strategy {
  Note: 'Logical model only; physical database technology is not selected.'
}

Table identity.accounts {
  id uuid [pk]
}

Table strategy.strategy_releases {
  id uuid [pk]
  owner_account_id uuid [not null]
}

Ref: strategy.strategy_releases.owner_account_id > identity.accounts.id
```

위 예시의 `uuid`는 논리적 불투명 식별자를 나타내는 DBML 표현이며 특정 DBMS 함수·생성 방식·저장 크기를 확정하지 않는다.

공통 규칙은 다음과 같다.

- 모든 테이블은 소유 schema를 명확히 가진다.
- 테이블 이름은 복수형 `snake_case`, 열 이름은 단수형 `snake_case`를 사용한다.
- 식별자는 외부 의미를 포함하지 않는 불투명 키를 사용한다.
- 돈·가격·수량·비율에 부동소수점 타입을 사용하지 않는다. 정확한 정밀도는 회계 검증 전까지 DBML Note로 미결정 근거를 남긴다.
- 모든 시각은 절대 시점과 해당 시장 기준 시각의 의미를 구분한다. DBMS별 timestamp 타입은 기술 선택 때 확정한다.
- 상태값은 허용 전이와 종료 상태를 Note 또는 명시적 상태 정의로 설명한다. DBMS 종속 enum을 미리 가정하지 않는다.
- 불변 테이블은 `updated_at`을 두어 수정 가능하다는 인상을 만들지 않는다.
- 정정·취소·무효화는 `original_*_id`, `reverses_*_id`, `supersedes_*_id`처럼 방향이 명확한 자기 또는 교차 참조로 표현한다.
- 외부 객체는 논리 객체 식별자, 내용 해시, 형식, 크기, 생성 시각과 계보를 갖는다. 공급자 URL이나 가변 파일 경로를 정본 키로 사용하지 않는다.
- 멱등성이 필요한 공식 효과는 안정적인 요청·사건 식별자와 적용 대상 범위의 유일성 제약을 표현한다.
- 다른 schema의 식별자를 참조할 수 있지만 대상 schema의 내부 상태를 대신 소유하거나 직접 덮어쓰는 테이블을 만들지 않는다.
- 조회용 집계·리더보드·대시보드 모델은 `derived`라고 명시하고 원본 재생성 근거를 참조한다. 별도 `read_model` schema는 실제 필요가 확인되기 전 만들지 않는다.

## 현재 상태와 불변 기록

각 도메인은 아래 세 종류를 구분한다.

1. 현재 제약 검사에 필요한 변경 가능한 상태
2. 과거 의미를 보존하는 추가만 가능한 공식 기록
3. 공식 기록에서 다시 만들 수 있는 파생 읽기 모델

현재 행과 공식 사건을 모두 저장하는 경우 두 값의 역할을 Note로 명시한다. 현재 행은 빠른 조회와 제약 검사를 위한 정본 상태일 수 있지만, 과거 공식 결과를 다시 쓰는 근거는 불변 사건·원장·잠긴 버전이다. 충돌하면 정의된 재계산·정정 절차를 사용하고 현재 행을 조용히 덮어써 과거를 바꾸지 않는다.

## 도메인 간 주요 참조 흐름

```text
identity.account
  → strategy.draft → strategy.validation → strategy.version
  → bot.bot → bot.bot_strategy → bot.event
  → trading.order → trading.fill
  → trading.ledger_transaction → trading.ledger_entry
  → trading.position_lot → trading.lot_consumption

market_data.dataset_manifest → bot.event / backtest.input_bundle
strategy.version → backtest.run
backtest.run → backtest.monthly_judgment_summary / backtest.performance_summary
backtest.run → backtest.detail_object_manifest → immutable backtest detail object
bot.bot → competition.participation → competition.evaluation_segment
bot.event / trading.* / backtest.* → operations.evidence_object_ref
```

도메인 간 관계는 위 흐름을 기본으로 하되, 순환 소유권을 피한다. 예를 들어 `bot`은 방 참여 상태를 가질 수 있지만 방 규칙의 정본은 `competition`이 소유하고, `competition`은 봇의 거래 원장을 복제하지 않고 평가 구간과 결과 참조만 소유한다.

## 원자성·실패 경계

- 전략 출시: 검증된 작업본 해시, 잠긴 전략 버전, 컴포넌트 버전 참조와 출시 사건이 일부만 생성되지 않아야 한다.
- 봇 평가: 판단 결과, 전략 상태 변경 후보, 주문 후보와 충돌 처리 결과는 봇 단위 원자 경계로 확정한다.
- 주문·체결: 비동기 결과는 새 봇 사건과 새 순번으로 추가하고 이전 사건을 수정하지 않는다.
- 원장 반영: 하나의 경제 사건에 대한 원장 거래와 균형 항목 묶음은 함께 확정한다.
- 방 평가 종료: 성과용 가상 청산과 실제 봇 중단·정산을 서로 다른 기록 종류와 참조로 분리한다.
- 객체 저장: RDB manifest가 객체의 존재와 해시를 검증하지 못하면 재현·상세 근거 사용을 실패 상태로 표시한다.
- 후속 알림·읽기 모델 갱신은 공식 원본과 함께 유실되지 않는 전달 의도를 기록하되 원본보다 먼저 정본이 되지 않는다.

## 작성 순서

`db/schema.dbml`은 관계의 중심축부터 다음 순서로 확장한다.

1. `identity`, `strategy`: 계정 식별 경계, 작업본·검증·잠긴 버전
2. `bot`: 봇 구성, 포함 전략, 상태와 공식 사건 순번
3. `trading`: 주문·체결·예약·복식 원장·전략 귀속·체결 묶음
4. `market_data`: 종목, 공급자, 데이터셋 manifest, 개정·계보·객체
5. `backtest`: 실행, 잠긴 입력, 월별 판단·성과 요약, 상세 객체 manifest
6. `competition`: 방 규칙, 참여, 평가 구간, 점수·순위·공개 자격
7. `operations`: 알림, RBAC, 감사, 문의·신고·이의제기, 증거 객체

각 단계마다 다음을 확인한 뒤 다음 schema로 진행한다.

- 제품 정책과 수명주기 누락 여부
- 변경 가능·불변·파생 데이터의 오분류 여부
- 도메인 소유권과 교차 참조 방향
- 필수 유일성·멱등성·종료 상태 제약
- 삭제·정정·무효화가 원본을 훼손하지 않는지
- 대용량 객체와 RDB manifest의 무결성 관계

## 검증 방법

- DBML 문법 검증과 참조 대상 존재 여부를 자동 검사한다.
- 모든 테이블이 선언된 schema 중 하나에 속하는지 검사한다.
- 공식 불변 기록에 갱신을 전제로 한 열이나 관계가 없는지 검토한다.
- 원장 거래·항목 균형, 출시 버전당 백테스트 한 개, 봇별 사건 순번, 활성 로그인 수단 유일성처럼 DBML만으로 완전히 강제하기 어려운 규칙은 계약·후속 테스트 의무로 등록한다.
- 제품 시나리오별로 생성·변경·불변·정정·종료 데이터 경로를 추적한다.
- dbdiagram을 사용하면 Git DBML에서 생성한 격리된 제안만 비교하고, 직접 편집 결과를 정본에 자동 반영하지 않는다.

## 이번 설계에서 확정하지 않는 내용

- RDB 제품과 버전
- DBMS별 schema 생성·권한 문법
- 실제 기본키 생성 알고리즘
- 숫자 정밀도와 반올림
- 인덱스·파티션·샤딩·복제
- 객체 저장 서비스와 열 지향 파일 형식
- 캐시·검색·메시지 제품
- 보존 기간과 물리 삭제 작업
- 마이그레이션·롤백 구현

위 항목은 논리 DBML과 품질·데이터 계약을 승인한 뒤 공식 근거와 기술 비교를 통해 결정한다.

## 승인 기준

이 설계가 승인되면 다음 단계에서 `db/schema.dbml`을 생성한다. 최초 DBML은 전체 도메인을 빈 이름만 나열하는 문서가 아니라 1~3단계의 핵심 관계인 `identity`·`strategy`·`bot`·`trading`을 먼저 완전한 논리 초안으로 만들고 검증한 뒤 나머지 schema를 순서대로 확장한다.
