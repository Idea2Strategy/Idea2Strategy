# 2.5 — 지표(feature) 백필 완료 (AWS Development)

## 언제 · 어디서

- 수행: `pjy008008` (data-pipeline·trading-engine 담당). 완료 보고 2026-08-08.
- 확인: `kcrmin` (루트). 2026-08-08, AWS Development 의 정본 DB `idea2strategy_runtime` 을
  직접 조회.
- 조회 경로: `idea2strategy-dev-core`(`i-03bb3f4a492227874`) 에서 SSM Run Command → 컨테이너
  psql → RDS. **RDS 는 VPC 안이라 로컬에서 닿지 않는다** — 이것이 원장 검사를 바꾼 이유다(§왜
  검사를 바꿨나).

## 관찰한 결과 — 실측

### 해상도별

```sql
select d.resolution, m.status, count(*)
  from market_data.feature_materializations m
  join market_data.feature_definitions d on d.id = m.feature_definition_id
 group by d.resolution, m.status order by d.resolution;
```

| resolution | status | count |
| --- | --- | --- |
| `1d` | `SUCCEEDED` | **725** |
| `1h` | `SUCCEEDED` | **725** |
| `30m` | `SUCCEEDED` | **725** |
| `4h` | `SUCCEEDED` | **725** |

**네 해상도 모두 725건이고 전부 `SUCCEEDED` 다.** `SUCCEEDED` 가 아닌 행은 한 건도 없다 —
위 그룹핑에 다른 status 가 나타나지 않았다.

### 총계와 결과 해시

```
total=2900  succeeded=2900  with_hash=2900
```

2,900건 전부 성공이고 **전부 결과 해시를 갖는다.** 해시가 없는 행은 0건이다. 이것이 중요한
이유는, 해시가 백테스트를 재현 가능한 입력에 고정하는 값이기 때문이다(INT01 §2 에서 같은
필드군이 문제였다).

### 고유 종목

```
select count(distinct instrument_id) from market_data.feature_materializations;  → 725
select count(*) from market_data.instruments;                                    → 725
```

**백필된 종목 수가 카탈로그의 종목 수와 같다.** 725 × 4 해상도 = 2,900 이 정확히 맞는다 —
빠진 종목이 없다는 뜻이다.

### 선행(2.4)도 같은 조회에서 확인했다

```
dataset_manifests: 30m 750 · 1h 749 · 4h 749 · 1d 749 — 전부 AVAILABLE
```

## 담당자 보고와의 대조

`pjy008008` 의 보고는 "725개 종목 × 4개 해상도, 총 2,900건, 해상도별 725건 모두 SUCCEEDED,
결과 해시 생성, 작업 큐와 DLQ 0건" 이었다. **위 조회가 그 숫자들과 일치한다.**

큐·DLQ 0건은 이 조회로 확인한 항목이 아니다 — 담당자 보고를 그대로 인용해 둔다. 확인이 필요하면
`aws sqs get-queue-attributes` 로 별도 확인한다.

## 재실행 금지

담당자가 명시적으로 요청했고, 근거가 있다. 백필은 종목·해상도마다 결과 해시를 고정하며, 그
해시가 이미 2,900건 모두 존재한다. 다시 돌리면 같은 입력에 새 행을 쓰거나 기존 해시를 흔들 수
있고, 그것은 이미 그 해시에 고정된 백테스트·평가의 재현성을 깨뜨린다.

**이 문서가 있는 동안 백필을 재실행하지 않는다.** 실행이 필요하면 왜 필요한지와 기존 2,900건을
어떻게 다룰지를 먼저 정한다.

## 왜 원장 검사를 바꿨나

이 카드의 검사는 로컬 DB 를 보는 `sql-equals` 였다.

```json
{"kind": "sql-equals", "expected": 4,
 "sql": "select count(distinct d.resolution) from market_data.feature_materializations m
         join market_data.feature_definitions d on d.id = m.feature_definition_id
         where m.status='SUCCEEDED'"}
```

`launch-status.ps1` 은 `DATABASE_URL`(또는 `PIPELINE_WORKER_DATABASE_URL`)로 psql 을 실행한다.
그 값이 가리키는 것은 **로컬 조합의 postgres** 이고, 정본 데이터가 있는 곳은 **AWS RDS** 다.
RDS 는 VPC 안이라 그 스크립트가 닿을 수 없다.

즉 검사는 틀린 답을 준 것이 아니라 **틀린 곳을 보고 있었다.** 로컬에는 백필이 없고, 있어야 할
이유도 없다 — 로컬에는 시장 데이터가 애초에 적재되지 않았다(§2.4 참조).

그래서 2.4·2.5 를 `manual` 로 바꾸고 완료 판정을 이 증거 파일의 존재로 옮겼다. AWS 에서 검증된
다른 카드들과 같은 방식이다(`INT02-aws.md`, `2.4-aws-state.md`).

**잃는 것을 분명히 적는다.** `manual` 은 파일이 있는지만 본다. SQL 검사만큼 강하지 않다. 그
차이를 메우는 것은 리뷰다 — 이 파일에 실행한 질의와 관찰한 숫자가 그대로 있어야 하고, 없으면
반려해야 한다(`docs/evidence/README.md`).

## 통과하지 못한 것

**백필된 값이 옳은지는 검증하지 않았다.** 이 문서가 말하는 것은 2,900건이 존재하고 상태가
`SUCCEEDED` 이며 해시가 있다는 것까지다. RSI 값이 실제로 맞는지, 라이브와 백테스트가 같은 값을
내는지는 다른 것이 확인한다 — 런타임 간 정합성은 §4 에서 고친 8건과
`scripts/integration/test_three_lane_feature_e2e.py`(CI 에서 매 PR 실행) 의 몫이다.

**큐·DLQ 0건은 담당자 보고 인용이다** — 위에 적었다.
