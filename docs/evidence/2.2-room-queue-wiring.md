# 2.2 — 방·운영자 큐 배선 실증

## 언제 · 어디서

- 2026-08-08, 로컬 조합(`compose.back.yml`, `--profile apps`).
- 루트 `9371714`. 서브모듈 `backend c5817d8`, `backtest-engine 5613ce4`,
  `data-pipeline a530d6b`, `trading-engine f806f0c`, `ui 7cf029a`.

## 왜 실증이 필요했나

`compose.back.yml` 은 relay 라우팅 맵을 `SPRING_APPLICATION_JSON` 으로 준다. 환경변수
이름은 Spring 맵 키를 담을 수 없기 때문이다 — relaxed binding 이 밑줄마다 점을 넣으므로
`OFFICIAL_BACKTEST_REQUESTED` 가 한 개의 이벤트 타입이 아니라 네 단계 중첩 키로 묶인다.

그 JSON 에는 백테스트 3개 타입만 있다. 방·기업행사 4개 타입은 `application.yaml` 의
`${ROOM_LEDGER_*_QUEUE_URL:}` 자리표시자로만 들어온다. `SPRING_APPLICATION_JSON` 은
`application.yaml` 보다 우선순위가 높으므로, 두 출처의 맵 키가 **병합**되는지 아니면 높은
쪽이 맵 전체를 **교체**하는지가 실제 동작을 갈랐다. 교체라면 `OutboxRelayWorker` 는
`publisher.routedEventTypes()` 에 없는 방 이벤트를 영원히 outbox 에 남겨두고, INT04 는
아무 오류 없이 조용히 실패한다.

문서를 읽어 추론하는 대신 넣어 봤다.

## 실행한 명령

네 이벤트 타입마다 outbox 행을 하나씩 넣고 relay 주기(1초) 를 기다렸다.

```bash
docker exec idea2strategy-postgres psql -U idea2strategy -d idea2strategy -c \
  "insert into operations.outbox_messages
     (owner_domain, aggregate_id, event_type, event_schema_version, payload_document,
      idempotency_key, payload_hash, producer_idempotency_key)
   values ('competition', gen_random_uuid(), 'ROOM_EVALUATION_ACCOUNT_OPEN_REQUESTED', '1',
      '{\"probe\":\"int04-routing\"}'::jsonb, 'probe-int04-routing-1',
      'probe-hash-int04-1', 'probe-producer-int04-1')"

docker exec idea2strategy-postgres psql -U idea2strategy -d idea2strategy -c \
  "select event_type, delivery_status, last_failure_code
     from operations.outbox_messages where idempotency_key like 'probe-%' order by event_type"

docker exec idea2strategy-localstack awslocal sqs get-queue-attributes \
  --queue-url http://localhost:4566/000000000000/room-ledger-open-request \
  --attribute-names ApproximateNumberOfMessages
```

## 관찰한 결과

큐 8개(4개 + DLQ 4개)가 `ready.d/10-create-queues.sh` 로 생성되었다.

```
room-ledger-open-request      room-ledger-open-request-dlq
room-ledger-opened            room-ledger-opened-dlq
room-ledger-rejected          room-ledger-rejected-dlq
corporate-action-approval     corporate-action-approval-dlq
```

네 타입 전부 발행되었다. 맵 키는 병합된다.

```
               event_type               | delivery_status | last_failure_code
----------------------------------------+-----------------+-------------------
 CORPORATE_ACTION_APPROVAL_DECIDED      | PUBLISHED       |
 ROOM_EVALUATION_ACCOUNT_OPENED         | PUBLISHED       |
 ROOM_EVALUATION_ACCOUNT_OPEN_REJECTED  | PUBLISHED       |
 ROOM_EVALUATION_ACCOUNT_OPEN_REQUESTED | PUBLISHED       |
```

첫 프로브 직후 `room-ledger-open-request` 깊이가 `0` → `1` 로 올라갔고,
`publish_attempt_count = 0`, `last_failure_code` 는 비어 있었다 — 재시도 없이 한 번에
나갔다는 뜻이다.

워커 안에서 보이는 값:

```
ROOM_LEDGER_OPEN_REQUEST_QUEUE_URL=http://localstack:4566/000000000000/room-ledger-open-request
ROOM_LEDGER_OPENED_QUEUE_URL=http://localstack:4566/000000000000/room-ledger-opened
ROOM_LEDGER_REJECTED_QUEUE_URL=http://localstack:4566/000000000000/room-ledger-rejected
CORPORATE_ACTION_APPROVAL_QUEUE_URL=http://localstack:4566/000000000000/corporate-action-approval
ROOM_LEDGER_RESULT_CONSUMER_ENABLED=true
```

## 정리

프로브 4행과 그 delivery attempt 를 지우고 큐 4개를 purge 했다. 이후
`outbox_messages where idempotency_key like 'probe-%'` 는 0 행이고 네 큐 모두 깊이 0 이다.
INT04 가 자기 메시지만 보게 하려면 이 정리가 필요하다.

## 통과하지 못한 것

없다. 다만 이 시험이 증명한 것은 **배선**이다 — outbox 에 들어간 방 이벤트가 올바른 큐로
나간다는 것까지다. 방을 실제로 만들어 backend 가 그 행을 스스로 쓰는지, 그리고
`RoomEvaluationAccountResultConsumer` 가 결과를 되받아 방 상태를 옮기는지는 INT04 의
몫이며 이 파일은 그것을 주장하지 않는다.
