# Idea2Strategy 데이터 모델 의사결정 기록

- 상태: 격리된 DBML 초안 작성 및 파서 검증 완료
- 대상 초안: `proposals/dbml-redesign/schema.draft.dbml`
- 비교 대상 정본: `db/schema.dbml`
마지막 갱신: 2026-07-27

## 문서 역할

이 문서는 데이터 모델을 만들면서 사용자가 선택한 아키텍처 결정, DBML 반영 상태, 아직 답을 받지 않은 선택지를 추적한다.

- 사용자는 Idea2Strategy의 DB 설계 담당자이며 데이터 모델의 구조적 선택을 최종 결정한다.
- Codex는 프로젝트 정본과 실제 구현을 먼저 조사하고, 임의 확정할 수 없는 DB 선택에는 상호 배타적인 A/B/C 대안과 추천안을 제시한다.
- 사용자가 확정한 답변만 데이터 모델 결정으로 기록하고 DBML에 반영한다.
- DB 설계 담당자라는 역할은 제품 정본 변경 권한이나 외부 근거가 필요한 법률·회계·라이선스 결정을 자동으로 의미하지 않는다.
- 제품 의미의 정본은 `specs/`와 `contracts/`다.
- 이 문서는 제품 정본을 새로 정의하거나 대체하지 않는다.
- 제품 정본에서 확인할 수 있는 내용은 사용자에게 다시 묻지 않는다.
- 합리적인 선택에 따라 제품 동작이나 데이터 소유권이 달라지는 경우에만 A/B/C로 질문한다.
- 사용자 답변을 받으면 이 문서와 격리된 DBML 초안을 같은 작업에서 수정하고 DBML 파서 검증을 실행한다. 보호된 정본은 fresh 제품 권한 승인 후 별도 작업에서만 수정한다.
- 회계 공식, 데이터 권리, 법률, 개인정보 보존 기간과 SLO처럼 외부 근거가 필요한 항목은 사용자 취향으로 확정하지 않는다.
- 기존 제품 정본과 달라지는 비즈니스 로직은 `proposals/dbml-redesign/product-meaning-changes.md`에 격리해 기록하고 운영자 컴퓨터에서 별도 검토·승인하기 전까지 정본으로 취급하지 않는다.

## 재점검한 프로젝트 이해

### 제품 경계

Idea2Strategy는 사용자가 시각적으로 만든 결정론적 전략을 서버가 미국 주식·ETF 시장 데이터로 평가하는 가상 트레이딩 봇 서비스다.

- 브라우저는 작성·실행 요청·조회 클라이언트이며 전략 평가나 주문 실행의 정본이 아니다.
- 사용자는 개별 주문이나 주문 의도를 직접 제출할 수 없다.
- 실제 거래, 투자 추천, 사용자 임의 코드 실행과 사용자 전략 평가 AI는 제품 범위가 아니다.
- 상세 전략, 보유 종목, 거래, 위험 설정과 백테스트 결과는 계정 소유자에게 비공개다.

### 계정과 로그인

- 활성 계정에는 확인된 이메일이 정확히 하나 필요하며, 하나의 계정은 현재 이메일을 하나만 소유한다.
- 사용자는 이메일 기반 로그인과 플랫폼이 지원하는 소셜 로그인을 모두 사용할 수 있다.
- 두 로그인 방식은 서로 다른 계정 종류가 아니며, 명시적 재확인과 연결 승인 후 같은 계정에 여러 로그인 수단을 연결할 수 있다.
- 소셜 로그인에서 받은 이메일이 기존 계정 이메일과 같다는 이유만으로 계정을 자동 병합하지 않는다.
- 계정 복구에는 확인 이메일, 이미 연결한 소셜 로그인 또는 사전 발급한 일회용 복구 코드만 사용한다.
- 서비스가 이메일 비밀번호, 세션, 확인 이메일 복구와 복구 코드를 직접 소유한다.
- 소셜 로그인은 서비스 계정에 OAuth/OIDC 제공자 식별자를 명시적으로 연결한다.
- 정확한 소셜 로그인 제공사와 OAuth/OIDC 설정은 아직 정해지지 않았다.

### 비밀방 참여

- 비밀방은 초대 링크와 초대 코드를 모두 지원한다.
- 유효한 링크·코드를 가진 사용자는 생성자의 개별 승인 없이 동일한 참여 자격 검사를 거쳐 참여한다.
- 생성자는 제출 마감 전까지만 초대를 폐기하거나 재발급할 수 있다.
- 모든 활성 초대는 제출 마감 또는 더 이른 방 종료 시 자동 만료한다.
- 링크 토큰과 코드 원문은 저장하지 않고 검증용 digest만 저장한다.

### 핵심 데이터 흐름

1. 사용자가 Basic 또는 Pro 전략 작업본을 저장한다.
2. 서버가 정확한 실행 의미 해시와 카탈로그 버전을 기준으로 검증한다.
3. 검증된 내용만 불변 전략 버전으로 출시한다.
4. 같은 트랜잭션에서 출시 버전당 최대 한 건인 공식 자동 백테스트를 `QUEUED` 상태로 만든다.
5. 사용자가 하나 이상의 불변 전략 버전, 전략별 예산과 공통 정책을 묶어 독립 봇을 실행한다.
6. 서버는 봇별 공식 사건 순서에 따라 전략들을 평가하고 주문 후보를 최종 처리한다.
7. 승인된 주문, 주문 상태 사건, 체결, 전략별 체결 귀속과 복식 원장을 PostgreSQL에 기록한다.
8. 큰 판단 입력·계산 추적, 시장 데이터와 백테스트 상세는 S3 불변 객체로 보존하고 PostgreSQL 매니페스트로 검증한다.
9. 방 참여는 이미 실행 중인 봇을 연결하는 방식이 아니라 같은 전략·설정을 사용한 별도의 초기 상태 봇을 생성하는 방식이다.
10. 방은 익명 봇만 비교하며 잠긴 점수 템플릿과 실제 라이브 가상 원장으로 순위를 계산한다.

## 확정된 데이터 모델 결정

### DMD-001 — NoSQL 책임

- 상태: 확정
- 사용자 선택: `1A`
- 결정: NoSQL은 봇 운영 개요, 현재 리더보드와 검색용 로그처럼 재생성 가능한 조회 Projection만 저장한다.
- PostgreSQL 정본: 전략 런타임 상태, 주문, 체결, 복식 원장, 방 규칙과 공식 결과
- S3 정본: 대용량 불변 원본과 상세 증거
- 장애 원칙: NoSQL 데이터가 유실되거나 지연돼도 공식 처리 결과는 바뀌지 않으며 PostgreSQL과 검증된 S3 객체에서 다시 생성한다.
- DBML 반영:
  - `operations.outbox_messages`
  - `operations.projection_checkpoints`
  - 각 PostgreSQL Projection 테이블은 공식 사건·원장보다 낮은 권위를 갖는다고 Note로 명시

### DMD-002 — 배치 작업 전달과 실행 제어

- 상태: 확정
- 사용자 선택: `2A`
- 결정: 외부 큐·스케줄러가 비동기 작업 전달과 예약 실행을 담당한다.
- PostgreSQL에는 범용 작업 큐를 두지 않고 각 도메인의 업무 실행 상태, 멱등성 키, 입력 버전, 결과와 실패 근거만 저장한다.
- 트랜잭션 경계: 업무 변경과 `operations.outbox_messages` 생성을 같은 PostgreSQL 트랜잭션으로 확정한다.
- 전달 원칙: 외부 큐 메시지는 정본이 아니며 중복 전달될 수 있다. 소비자는 도메인 실행 식별자와 멱등성 키로 중복 효과를 방지한다.
- DBML 반영:
  - 제거: `operations.jobs`, `operations.job_attempts`, `operations.job_checkpoints`
  - 유지: `operations.outbox_messages`, `operations.projection_checkpoints`
  - 도메인 업무 기록: 백테스트 실행, 시장 데이터 파이프라인, 성과 스냅샷, 리더보드 스냅샷, 알림 전달

### DMD-003 — 이메일·소셜 인증 운영

- 상태: 확정
- 사용자 선택: `B`
- 결정: 서비스가 이메일 비밀번호, 세션, 확인 이메일 기반 비밀번호 복구와 일회용 복구 코드를 직접 관리한다.
- 2026-07-27 추가 결정: 계정당 현재 이메일은 정확히 하나이며 다중 이메일·대표 이메일 모델은 사용하지 않는다.
- 소셜 로그인: 승인된 OAuth/OIDC 제공자의 불변 subject를 서비스 계정에 명시적으로 연결한다. 제공 이메일 일치만으로 기존 계정과 자동 병합하지 않는다.
- 비밀정보 저장 원칙:
  - 비밀번호는 메모리 경화 해시와 해시 매개변수만 저장한다.
  - 세션 토큰, 이메일 확인 토큰, 비밀번호 재설정 토큰과 복구 코드는 원문 대신 digest만 저장한다.
  - 소셜 access/refresh token은 현재 제품 요구에 없으므로 PostgreSQL에 영구 저장하지 않는다.
- DBML 반영:
  - `identity.account_emails.account_id`를 공유 PK로 사용하여 계정당 이메일을 최대 한 행으로 제한
  - `identity.email_verification_requests`로 재발송 가능한 확인 요청 이력을 이메일 현재 상태와 분리
  - PASSWORD 로그인은 해당 계정의 단일 확인 이메일을 사용하며 별도 `account_email_id`를 중복 저장하지 않음
  - `identity.auth_providers`로 PASSWORD와 OIDC 제공자 설정을 분리
  - 소셜 제공자 subject는 이메일과 분리된 `provider_subject_hmac`으로 식별
  - `identity.sessions.authenticated_by_login_identity_id`로 세션을 발급한 로그인 수단 기록
  - `identity.password_reset_requests`로 확인 이메일 기반 단일 사용 복구 요청의 만료·검증·소비 상태 기록

### DMD-004 — PostgreSQL 기본 식별자

- 상태: 확정
- 사용자 선택: `B`
- 결정: 독립 엔터티의 대리 PK는 PostgreSQL `gen_random_uuid()`로 생성하는 UUIDv4를 사용한다.
- 예외:
  - 부모 행과 생명주기가 같은 확장 테이블은 부모 UUID를 공유 PK로 사용한다.
  - 순수 관계 테이블은 의미 있는 FK 조합을 복합 PK로 사용한다.
  - 외부 공급자 ID와 도메인 sequence는 UUIDv4로 대체하지 않는다.
- 순서 원칙: UUIDv4 값 자체에는 시간 순서가 없으므로 생성·처리 순서는 `created_at`, `occurred_at`, `event_sequence` 같은 명시적 컬럼으로 판단한다.
- 운영상 비용: UUIDv7보다 B-tree 삽입 지역성이 낮다. 대용량 사건·원장 테이블은 시간/소유자 기반 인덱스와 파티셔닝을 별도로 설계하고 인덱스 크기·페이지 분할·bloat를 관측한다.
- DBML 감사 결과: 독립 엔터티 UUID PK는 이미 모두 `gen_random_uuid()`를 사용하고 있어 PK 컬럼 변경은 필요하지 않았다.

### DMD-005 — 파티션 내부 전략 소유권

- 상태: 확정된 DBML 재설계 입력, 제품 정본 조정 전 제안
- 사용자 선택: 기존 질문 1의 `B`를 구체화한 2026-07-27 봇 스키마 재검토 질문 1의 `A`
- 결정:
  - 하나의 봇은 여러 파티션을 소유한다.
  - 하나의 파티션은 여러 전략을 소유한다.
  - 전략은 정확히 하나의 파티션에 종속되는 블록 묶음이며 독립 라이브러리 항목이나 버전 관리 대상이 아니다.
  - 다른 파티션이 같은 전략 행이나 블록 묶음을 공유하거나 재사용하지 않는다.
  - 봇·파티션·전략을 복사할 때는 새 식별자로 단순 복제하고 원본 참조, 계보 또는 버전 연결을 남기지 않는다.
- 예정 DBML 반영:
  - 현재 `bot.bot_strategies` 직접 연결을 제거한다.
  - `bot.bot_partitions`와 `partition_id NOT NULL`인 `bot.strategies` 직접 소유 구조를 도입한다.
  - 파티션 소유 FK는 `NOT NULL`로 두고, 다른 파티션의 전략·블록을 교차 참조하지 못하도록 복합 FK 또는 동등한 데이터베이스 제약을 둔다.
  - 주문 의도, 체결 귀속, 포지션, 예산 예약과 원장 추적에 파티션 및 파티션 전략 식별자를 전파한다.
- 정본 차이:
  - 현재 제품 정본은 독립 전략 작성·출시·재사용 흐름을 전제로 한다.
  - 이 결정은 해당 의미와 조정되기 전까지 DBML 재설계 제안으로만 취급하며 `specs/`와 `contracts/`를 수정하거나 승인·통합된 제품 결정으로 표현하지 않는다.
- 적용 시점: 종목 범위, 예산 격리, 블록 저장과 출시 수명주기 질문이 끝난 뒤 일관된 DBML 초안으로 한 번에 반영한다.

### DMD-007 — 파티션 예산 상한

- 상태: 확정된 DBML 재설계 입력, 제품 정본 조정 전 제안
- 사용자 선택: 질문 3의 `A`
- 결정:
  - 봇의 초기 자본을 기준으로 각 파티션에 백분율 상한을 설정한다.
  - 한 봇의 파티션 상한 합계는 100% 이하여야 하며 미배정 자금은 봇의 가용 현금으로 남긴다.
  - 예산은 파티션까지만 할당하고 Basic·Pro 모두 하위 전략에는 예산이나 별도 상한을 배정하지 않는다.
  - 같은 파티션의 전략들이 만든 주문 의도는 하나의 파티션 예산 경계를 함께 사용한다.
  - 사용하지 않은 예산을 다른 파티션이 빌려 쓰지 않는다.
  - 예산 사용액은 체결·보유 금액뿐 아니라 미체결 주문에 예약한 금액까지 포함한다.
- 예정 DBML 반영:
  - 비율은 부동소수점이 아니라 정수 basis point 또는 동등한 고정 정밀도 값으로 저장하고 `0..10000` 범위를 강제한다.
  - 파티션 상한 합계는 단일 행 `CHECK`만으로 강제할 수 없으므로 완성된 봇 집합 생성 트랜잭션과 지연 제약 트리거로 검증한다.
  - 주문 생성 전에 파티션·봇 순서로 현금·보유수량·숏 차입·담보를 예약하는 `trading.resource_reservations`를 두고 주문의 종료·거절·체결에 따라 추가 전용 `reservation_events`로 멱등적으로 소비 또는 해제한다. `flow_id`는 예산 경계가 아니라 발생 Flow 귀속만 기록한다.
  - 공식 복식 원장은 봇 단위 정본을 유지하되 파티션 예산과 전략 발생 귀속을 함께 기록하고, 파티션 현재 사용액 Projection은 원장과 활성 예약에서 재구성할 수 있게 한다.
  - 전략별 예산 컬럼과 `trading.strategy_budget_projections`는 두지 않는다.
- 불변 조건:
  - `파티션 사용액 + 파티션 활성 예약액 <= 파티션 상한`
  - `봇 사용액 + 봇 활성 예약액 <= 봇 가용 자본`

### DMD-008 — 시장가 주문 예산 예약과 정산

- 상태: 확정
- 사용자 결정: 고정 `0.05%` 슬리피지와 체결가격에 포함되지 않는 별도 Buying Power 예약 완충액을 사용한다.
- 결정:
  - 시장가 주문 유형을 IOC 시장성 지정가 주문으로 변환하지 않는다.
  - 랜덤 슬리피지를 사용하지 않고 매수에는 `+0.05%`, 매도에는 `-0.05%`의 고정 슬리피지를 적용한다.
  - 주문 승인 전에 현재 호가, 고정 슬리피지, 예상 수수료와 별도 Buying Power 완충액을 사용해 파티션·봇 예산을 원자적으로 예약한다.
  - Buying Power 완충액은 미체결 주문의 자금 예약에만 사용하며 체결가격, 수수료, 손익 또는 성과 계산에 반영하지 않는다.
  - 체결 시점의 최신 유효 가격에 고정 슬리피지와 수수료를 적용해 필요한 금액을 다시 계산한다.
  - 재계산 금액이 예약액보다 작으면 차액을 멱등적으로 해제한다.
  - 재계산 금액이 예약액 또는 단계별 예산 상한을 넘으면 체결 전에 수량을 축소하고, 최소 주문 수량이나 정책 조건을 충족하지 못하면 주문을 거절한다.
  - 신뢰 가능한 최신 가격이 없거나 오래됐거나 필요한 예약액을 계산할 수 없으면 주문을 승인하거나 체결하지 않는다.
  - Buying Power 완충액은 플랫폼이 관리하는 버전 고정 비율로 계산하며 사용자 또는 Pro 전략이 변경할 수 없다.
  - 완충액 산식은 `기준 주문금액 × buffer_bps / 10,000`이고 통화 최소 단위에 맞춰 보수적으로 올림한다.
  - 총 예약액은 `현재 가격에 고정 0.05% 슬리피지를 반영한 예상 체결금액 + 예상 수수료 + 완충액`이다.
  - 정확한 `buffer_bps` 값은 스키마 상수로 하드코딩하지 않고 불변 정책 버전 데이터로 관리하며 주문은 승인 당시 버전을 고정한다.
- 예정 DBML 반영:
  - `trading.buying_power_buffer_policy_versions`에 버전, `buffer_bps`, 반올림 규칙 버전, 유효 기간, 규칙 해시와 게시 시각을 둔다.
  - `trading.resource_reservations`에 Flow, 파티션, 봇, 주문 의도, 자원 종류, 기준 호가 금액, 고정 슬리피지 금액, 예상 수수료, 완충액, 예약 금액 또는 수량, 가격·데이터 버전, 완충·숏 규칙 버전과 현재 상태를 둔다. 모든 소비·해제는 `reservation_events`, 주문 배분은 `order_reservation_allocations`, 보유 로트 예약은 `reservation_lot_allocations`에 남긴다.
  - `trading.orders`에 주문 시점 예약 근거와 고정 슬리피지 규칙 버전을 잠근다.
  - `trading.fills`에는 체결 기준 가격, 고정 슬리피지 금액, 실제 수수료와 최종 체결 금액을 분리해 기록하고 Buying Power 완충액을 기록하지 않는다.
  - 주문 승인, 예약 생성과 공식 봇 사건을 같은 PostgreSQL 트랜잭션에서 확정한다.
  - 체결 승인, 수량 축소 또는 거절, 예약의 원장 전환과 차액 해제를 같은 멱등 처리 경계에서 확정한다.
  - 체결 합계와 비용이 활성 예약액 또는 전략·파티션·봇 상한을 넘지 못하도록 실행 계층과 데이터베이스 불변 조건을 함께 검증한다.
- 미결정:
  - 정확한 호가 기준면과 가격·수수료·수량 정밀도

### DMD-009 — 동일 종목 주문 의도 상계

- 상태: 확정
- 사용자 선택: 질문 4의 `A`
- 결정:
  - 한 평가 주기의 모든 전략은 동일하게 고정된 입력 상태와 시장 데이터 스냅샷을 기준으로 주문 의도를 만든다.
  - 전략별 원래 주문 의도와 해당 파티션 예산 검사 결과, 거절·축소 사유는 append-only 공식 기록으로 보존한다.
  - 예산과 보유 수량 검사를 통과한 의도를 봇·종목 단위로 모아 같은 방향은 합산하고 반대 방향은 결정론적으로 상계한다.
  - 완전히 상계된 수량은 외부 또는 가상 시장 주문과 체결을 만들지 않고 `NETTED` 판단 근거만 남긴다.
  - 상계 후 실제 주문과 체결은 승인된 잔여 의도 수량 또는 금액 비율에 따라 전략과 파티션에 결정론적으로 귀속한다.
  - 상계는 형제 파티션 사이의 예산이나 현금을 이전하지 않으며 전략별 포지션 lot 또는 손익 귀속도 이전하지 않는다.
  - 매도 또는 숏 상환 의도는 해당 전략에 귀속된 보유 lot 범위만 사용할 수 있다.
- 예정 DBML 반영:
  - `trading.order_intent_batches`가 평가 실행, 고정 입력 해시, 충돌 정책 버전과 최종 결과 해시를 소유한다.
  - `trading.order_intents`가 전략, 파티션, 종목, 원래 요청값, 승인값, 상계값, 최종 잔여값과 결정 사유를 보존한다.
  - `trading.orders`는 상계 후 하나 이상의 잔여 의도에서 생성되며 `trading.order_intent_allocations`가 주문을 구성하는 의도별 예정 수량과 결정 순서를 고정한다.
  - 주문별 `order_intent_allocations.allocated_quantity` 합계는 `orders.requested_quantity`와 일치해야 하며, 이 교차 행 불변식은 지연 제약 또는 마이그레이션 트리거로 강제한다.
  - `trading.capital_reservations`는 구매력 예약이 필요한 승인 의도마다 존재하고 주문이 연결된 뒤에는 같은 `(order_id, intent_id)`의 예정 배분을 참조해야 한다.
  - `trading.fill_allocations`는 각 실제 체결을 기존 `(order_id, intent_id)` 예정 배분에 직접 연결한다. 구매력 예약이 필요한 의도는 같은 의도의 예약도 참조하며, 현금 예약이 필요 없는 청산 의도는 예약 참조를 두지 않는다. 체결별 배분 합계는 체결 수량·금액·수수료와 일치하고, 주문·의도별 누적 체결 배분은 예정 수량을 초과할 수 없다.
  - 공식 원장 항목, 포지션 lot과 lot 변동은 `fill_allocations`를 직접 참조해 실제 체결이 어떤 전략·파티션에 귀속됐는지 끊기지 않게 보존한다.
  - 같은 입력과 규칙 버전에는 같은 상계·배분 결과가 나오도록 정렬 키, 반올림 규칙과 잔여 수량 배분 규칙을 버전으로 고정한다.

### DMD-010 — 전략 블록 문서 저장

- 상태: 확정
- 사용자 선택: 질문 5의 `A`
- 결정:
  - 블록, 포트, 연결, 타입 지정 매개변수와 실행 의미가 있는 그룹은 전략 단위 `semantic_document JSONB`에 하나의 aggregate로 저장한다.
  - 전략 내부 요소의 화면 좌표, 크기, viewport, zoom, 그룹 배치·접힘, 선택 상태와 edge routing hint는 별도 `layout_document JSONB`에 저장한다. 실행 의미를 가진 `semantic_document`와 분리하며, 자세한 규칙은 DMD-030을 따른다.
  - 봇 캔버스에서 파티션과 전략 카드의 배치는 관계형 컬럼 `position_x`, `position_y`로 저장하며 `display_order`를 사용하지 않는다.
  - 블록마다 관계형 행을 만들거나 NoSQL에 별도 변경 가능한 전략 정본을 두지 않는다.
  - 저장할 때 카탈로그 버전에 맞는 JSON Schema, 타입, DAG, 필수 최종 주문 처리 경로와 제품 정책을 검증한다.
  - 봇에 포함되는 전략은 완성·검증된 의미 문서, 카탈로그와 모든 실행 의존성을 새 행으로 함께 삽입하고 의미 해시와 전체 구성 해시를 보존한다.
  - 종목, 데이터 요구사항, 재사용 컴포넌트와 정책 버전처럼 FK 무결성·영향 분석·실행 준비에 필요한 의존성만 관계형 테이블로 투영한다.
- 예정 DBML 반영:
  - `bot.strategies`는 `partition_id NOT NULL`인 파티션 직접 소유 자식이며 별도 버전·공유·원본 참조 컬럼을 두지 않는다.
  - 파티션 종속 전략에 `semantic_document`, `semantic_hash`, `block_catalog_version_id`와 `configuration_hash`를 둔다. 카탈로그 버전은 전략 버전이 아니라 블록 정의·검증 규칙을 재현하기 위한 기술적 핀이다.
  - 파티션과 전략에 `position_x`, `position_y`를 두고 좌표 중복을 허용한다. `id`는 동일 좌표의 결정적 조회 순서를 위한 타이브레이커로만 사용한다.
  - 관계형 의존성 행은 봇 생성·검증 PostgreSQL 트랜잭션에서 함께 삽입하고 문서 해시를 통해 일치 여부를 검증한다.
  - JSONB GIN 인덱스는 실제 운영 질의가 확인된 경로에만 제한적으로 두고, 소유자·파티션·상태 조회에는 일반 B-tree 인덱스를 사용한다.
  - NoSQL에는 PostgreSQL의 불변 봇 구성과 검증된 객체에서 재생성 가능한 검색·목록 Projection만 저장한다.

### DMD-011 — 완성된 구성으로 봇 생성

- 상태: 확정된 DBML 재설계 입력, 제품 정본 조정 전 제안
- 사용자 선택: 질문 6의 `C` 이후 확정한 후속 요구사항이 직전 잠금·복사 계보 결정을 대체한다.
- 결정:
  - 별도의 봇 구성 버전, 파티션 버전과 전략 버전 테이블을 만들지 않는다.
  - 봇은 포함된 모든 전략이 완성되고 출시 검증을 통과한 뒤에만 생성한다.
  - 생성 트랜잭션에서 봇 전체 계층, 예산 합계, 전략 문서, 종목·데이터 의존성, 정책 버전과 실행 가능성을 검증하고 새 식별자로 모든 구성 행을 삽입한다.
  - 봇은 완성도와 실행 가능성 검증을 모두 통과한 생성 트랜잭션이 커밋되면 즉시 `RUNNING`으로 시작하고 `DRAFT`, `LOCKING`, `WAITING`, `PAUSED` 상태를 사용하지 않는다.
  - 생성된 실행 의미는 처음부터 불변이며 별도의 잠금 시각이나 잠금 사건을 기록하지 않는다. 표시·운영 정보의 수정 범위는 DMD-022를 따른다.
  - 검증, 구성 삽입, 최초 공식 사건과 Outbox 생성 중 하나라도 실패하면 전체 트랜잭션을 롤백한다.
  - 봇·파티션·전략 복사·붙여넣기는 새 식별자를 가진 독립 데이터 집합을 만들며 원본 FK, 계보 또는 버전 연결을 남기지 않는다.
  - 원본 런타임 상태, 현금, 예약, 주문, 체결, 포지션, 원장과 성과는 복사하지 않는다.
- 예정 DBML 반영:
  - `bot.bots`는 소유권과 실행 이후 수명주기만 유지하고 `last_committed_event_sequence` 같은 구성 버전·커서 열을 두지 않는다.
  - `bot.launch_configurations`, `bot.bot_partitions`와 파티션 종속 전략은 생성 시점부터 `NOT NULL` 구성 해시를 가진 불변 행으로 삽입한다.
  - 실행 의미 열의 `UPDATE`와 실행 구성 행 `DELETE`를 항상 거절하고, DMD-022의 표시·운영 정보 수정과 수명주기 상태 변경, append-only 런타임 기록만 별도 허용하는 권한·트리거를 마이그레이션에 둔다.
  - `copied_from_bot_id`, `copied_from_partition_id`, `copied_from_strategy_id`와 이에 대한 자기 참조 FK를 두지 않는다.
- 정본 차이:
  - 현재 제품 정본은 별도의 불변 전략 출시 버전과 출시 버전당 공식 자동 백테스트를 전제로 한다.
  - 이 결정과 백테스트 단위가 정본과 조정되기 전까지 DBML 재설계 제안으로만 취급하고 승인·통합된 제품 의미로 표현하지 않는다.

### DMD-012 — 잠긴 봇 전체 구성 공식 백테스트

- 상태: 확정된 DBML 재설계 입력, 제품 정본 조정 전 제안
- 사용자 선택: 질문 7의 `A`
- 결정:
  - 공식 자동 백테스트의 입력 단위는 개별 전략이나 파티션이 아니라 잠긴 봇 전체 구성이다.
  - 하나의 잠긴 봇에는 최대 하나의 공식 자동 백테스트 실행만 생성한다.
  - 백테스트는 모든 파티션, 파티션 예산 상한, 전략 블록 문서, 종목 선택, 주문 충돌·상계, Buying Power 예약, 고정 슬리피지, 수수료와 회계 규칙 버전을 함께 재현한다.
  - 완성된 봇 집합 생성 트랜잭션에서 공식 백테스트 `QUEUED` 행과 Outbox를 함께 생성하여 일부만 존재하는 상태를 방지한다.
  - 백테스트는 라이브 봇의 현금, 예약, 주문, 체결, 포지션, 원장이나 런타임 전략 상태를 읽거나 변경하지 않고 독립 초기 상태에서 실행한다.
  - 입력 데이터나 필요한 블록 지원이 부족하면 임의 대체·부분 전략 제외 없이 명시적인 실패 또는 `UNAVAILABLE` 결과를 남긴다.
  - 같은 구성 해시, 시장 데이터, 계산, 비용, 슬리피지, Buying Power와 회계 규칙 버전에는 재현 가능한 결과가 나와야 한다.
- 예정 DBML 반영:
  - `backtest.runs`는 잠긴 `bot_id`를 유일하게 참조하고 주문 당시 `configuration_hash`와 모든 실행 규칙 버전을 고정한다.
  - 실행 상태, 시도, 잠긴 입력 데이터셋, 시작·종료 시각, 실패 코드, 월별 판단 요약과 압축된 성과 요약은 PostgreSQL에 저장한다.
  - 대용량 거래, 재생 원장, 포지션 스냅샷, 계산 시계열과 상세 판단 근거는 불변 S3 객체로 저장하고 PostgreSQL 매니페스트가 해시·크기·형식·스키마·계보를 검증한다.
  - 백테스트용 주문·체결·원장을 라이브 `trading` 테이블에 섞지 않고, 상세 객체와 백테스트 전용 요약 관계로 분리한다.
  - `UNIQUE (bot_id)`와 잠긴 구성 해시 일치 검증으로 같은 봇의 공식 실행 중복 생성을 차단한다.
- 정본 차이:
  - 현재 제품 정본의 출시 전략 버전당 자동 백테스트 규칙을 봇 전체 구성당 자동 백테스트로 바꾸는 제안이다.
  - 제품 정본 승인과 조정 전까지 DBML 제안으로만 취급한다.

### DMD-013 — 자동 백테스트와 봇 실행의 독립 수명주기

- 상태: 확정된 DBML 재설계 입력, 제품 정본 조정 전 제안
- 사용자 선택: 질문 8의 `A`
- 결정:
  - 완성·검증된 봇 집합 생성이 성공하면 공식 자동 백테스트를 큐에 넣고 봇은 백테스트 완료를 기다리지 않고 즉시 독립적으로 실행한다.
  - 봇 생성 트랜잭션은 구성 검증, 계정·방 자격, 라이브 데이터 가용성과 실행 인프라 준비 상태를 확인하지만 백테스트 상태를 실행 조건으로 사용하지 않는다.
  - 백테스트의 지연, `FAILED` 또는 `UNAVAILABLE`은 사용자에게 명시적으로 표시하고 감사 근거를 남기되 실행 중인 봇의 수명주기나 공식 라이브 원장을 변경하지 않는다.
  - 봇 중단 또는 실패도 이미 시작한 백테스트 실행을 취소하거나 결과를 숨기지 않는다.
  - 봇과 백테스트는 같은 잠긴 구성 해시를 참조하지만 서로의 현금, 주문, 체결, 포지션, 원장과 런타임 상태를 공유하지 않는다.
- 예정 DBML 반영:
  - `bot.bots.lifecycle_status`와 `backtest.runs.status`를 독립 상태 기계로 유지하고 서로를 FK 기반 상태 전이 조건으로 만들지 않는다.
  - 불변 봇 실행 의미, 백테스트 `QUEUED`, 봇 실행 요청과 각 Outbox 메시지는 하나의 원자 트랜잭션에서 생성한다.
  - 외부 큐·스케줄러는 봇 시작과 백테스트 실행을 별도 소비자·멱등성 키로 전달한다.
  - 사용자 조회에는 같은 구성 해시를 기준으로 봇 상태와 백테스트 상태를 함께 표시할 수 있지만 NoSQL 조회 Projection이 공식 상태를 소유하지 않는다.
- 비즈니스 로직 전달:
  - 이 결정과 기존 정본의 차이는 `proposals/dbml-redesign/product-meaning-changes.md`에 격리해 운영자 컴퓨터에서 후속 검토하도록 기록한다.

### DMD-014 — 시장 데이터 Stream·S3·NoSQL 경계

- 상태: 확정
- 사용자 선택: 질문 9의 `A`
- 결정:
  - 외부 스트림 또는 메시지 브로커가 실시간 시장 데이터 전달과 소비자 확장을 담당한다.
  - 원천·정규화·조정 시장 데이터와 대차 데이터의 불변 개정본은 S3 호환 객체 저장소가 정본이다.
  - NoSQL은 최근 시세, 봇 조회와 낮은 지연 읽기를 위한 Hot Projection만 저장하며 유실·지연돼도 공식 결과가 바뀌지 않는다.
  - PostgreSQL은 종목, 공급자·피드, 데이터셋 명세와 개정, 기간, 품질, 계보, 파이프라인 실행, S3 객체 위치·버전·해시·크기·형식과 Projection 체크포인트를 소유한다.
  - 원시 tick·quote·bar·borrow 시계열 본문과 대용량 배치 결과를 PostgreSQL 행으로 중복 저장하지 않는다.
  - 스트림, NoSQL과 외부 큐는 전달·조회 인프라이며 금액, 주문, 체결, 원장 또는 공식 판단의 정본이 아니다.
  - 공식 봇 판단은 실제 사용한 최소 관측값, 관측 시각, 공급자·피드, 데이터 버전과 내용 해시를 봇 사건 또는 불변 증거 객체에 고정한다.
- 일관성 규칙:
  - 생산자는 고유 객체 키에 업로드하고 내용 해시·크기·스키마·기간을 검증한 뒤 PostgreSQL 트랜잭션에서 객체와 데이터셋 매니페스트를 `AVAILABLE`로 확정한다.
  - 도메인 매니페스트 확정과 Outbox 생성을 같은 트랜잭션에서 처리한다.
  - NoSQL Projection은 커밋된 Outbox 또는 검증된 스트림만 소비하며 at-least-once 전달에 대비해 데이터셋 개정과 사건 식별자로 멱등 처리한다.
  - Projection 진행 상태와 실패는 `operations.projection_checkpoints`에 기록하고 NoSQL 전체를 S3와 PostgreSQL 매니페스트에서 재생성할 수 있어야 한다.
  - 객체는 동일 키 덮어쓰기를 정본 개정 방식으로 사용하지 않고 새 객체·새 개정과 명시적 계보를 만든다.
- 예정 DBML 반영:
  - 현재 관계형 시계열 본문 테이블을 제거하거나 데이터셋·객체 매니페스트 참조로 대체한다.
  - `storage.objects`, `market_data.dataset_manifests`, `market_data.dataset_objects`, `market_data.dataset_lineage`, `market_data.pipeline_runs`, `market_data.quality_incidents`와 `operations.projection_checkpoints`를 일관된 상태·해시 모델로 정리한다.
  - NoSQL 내부 테이블 구조는 PostgreSQL DBML에 정본 테이블처럼 포함하지 않고 외부 Projection 계약과 체크포인트만 표현한다.

### DMD-015 — S3 분석 객체 Parquet·무압축

- 상태: 현재 초안 확정, production 배포 전 비용·성능 재검증 필요
- 사용자 선택: 질문 10 수정안 — 파일 형식은 Parquet, 압축은 우선 사용하지 않는다.
- 결정:
  - 대용량 표 형식 시장 데이터, 백테스트 거래·포지션·재생 원장과 계산 시계열의 기본 파일 형식은 Apache Parquet다.
  - 현재 기본 compression codec은 명시적인 `UNCOMPRESSED`이며 작성 라이브러리의 암묵적 기본값을 사용하지 않는다.
  - 파일 형식과 압축 코덱은 별도 메타데이터로 관리하여 이후 새 데이터셋 개정부터 ZSTD 또는 Snappy 같은 코덱을 도입할 수 있게 한다.
  - 기존 불변 객체를 새 코덱으로 덮어쓰지 않고 새 객체·새 데이터셋 개정·명시적 계보로 재작성한다.
  - 비정형 판단 증거처럼 Parquet에 맞지 않는 객체는 별도 media type과 스키마 버전을 매니페스트에 기록한다.
- 예정 DBML 반영:
  - `storage.objects` 또는 도메인 객체 매니페스트에 `file_format`, `compression_codec`, `schema_version`, `content_hash`, `byte_size`, 행 수와 시간·종목 범위를 둔다.
  - `compression_codec`에는 현재 `UNCOMPRESSED`를 명시하고 null이나 작성기별 기본값을 허용하지 않는다.
  - 객체를 읽는 실행은 매니페스트의 실제 형식·코덱과 Parquet footer를 검증하고 불일치하면 사용하지 않는다.
- production 재검증:
  - 대표 시장 데이터와 백테스트 상세로 객체 크기, S3 저장·전송 비용, 스캔 처리량, CPU, 메모리와 읽기 지연을 측정한다.
  - 비용 또는 처리량 목표를 충족하지 못하면 기존 객체는 보존하고 새 개정부터 버전이 고정된 압축 코덱을 도입한다.
  - 이 성능 검증이 끝나기 전에는 무압축 선택만으로 production-ready가 입증됐다고 표현하지 않는다.

### DMD-016 — S3 Parquet 다단계 논리 분할과 불변 Compaction

- 상태: 확정
- 최신 사용자 결정: 시장 데이터 수집 객체를 일 단위로 게시할 수 있고, 누적된 작은 파일은 ET 달력 기준 주·월·연 단위로 불변 Compaction하여 장기 백테스트의 파일 열기 비용을 줄인다. 이전의 주 단위 전용 결정은 이 결정으로 대체한다.
- 결정:
  - 시장 데이터 객체는 `DAY`, `WEEK`, `MONTH`, `YEAR` 논리 파티션을 지원한다.
  - 모든 경계는 미국 동부 시각 ET 달력을 사용한다. 일은 해당 날짜, 주는 월요일, 월은 1일, 연은 1월 1일에 시작하며 종료 경계는 미포함이다.
  - 실시간 수집 데이터는 불변 마이크로배치 또는 일 단위 `part` 객체로 계속 게시하며 주·월·연 마감까지 S3 게시를 미루지 않는다.
  - 작은 객체가 누적되면 배치가 일→주, 주→월, 월→연 또는 검증된 동등 경로로 새 최적화 객체를 생성한다.
  - Compaction은 원본 객체를 덮어쓰지 않고 새 저장 객체, 새 데이터셋 개정, Manifest 계보와 파일 단위 계보를 만든다.
  - 이미 실행된 백테스트는 잠근 Manifest와 객체를 계속 사용하며 Compaction 이후의 객체로 소급 교체하지 않는다.
  - 하나의 공개 Manifest는 같은 `shard_key`와 관측 기간에 겹치는 일·주·월·연 표현을 함께 선택하지 않는다. 필요한 범위에서 가장 큰 검증 완료 파티션을 사용하고 경계 구간만 더 작은 파티션으로 채울 수 있다.
  - 700개 이상 종목은 종목마다 파일을 만들지 않고 결정론적인 종목 shard에 배치한다. shard 수와 목표 객체 크기는 대표 10년 백테스트의 파일 열기 수, 범위 읽기, 처리량과 재작성 비용을 측정해 정한다.
  - 휴장일이나 단축 거래일이 있어도 달력 경계를 유지하며 Manifest와 객체 메타데이터가 실제 포함 거래일과 관측 기간을 기록한다.
- 논리 키:
  - 시장 데이터: `dataset/revision/layer/resolution/granularity/partition_start/partition_end/shard/part`
  - 백테스트 상세: `run_id/record_type/week_start_date/part`
  - 객체 키 문자열은 탐색 보조 수단이며 PostgreSQL 매니페스트의 객체 ID, 버전과 내용 해시가 권위 있는 참조다.
- 예정 DBML 반영:
  - 시장 데이터 객체 연결에는 `partition_granularity`, `partition_start`, `partition_end`, `period_start`, `period_end`, `shard_key`, `part_number`, 행 수와 객체 참조를 둔다.
  - `market_data.dataset_object_lineage`가 Compaction 결과 객체와 모든 입력 객체 및 실행 파이프라인을 연결한다.
  - `partition_start < partition_end`, `period_start < period_end`와 선택한 ET 달력 경계 정합성을 ingestion 계층과 데이터베이스 제약 함수로 강제한다.
  - 동일 데이터셋 개정·granularity·partition·shard·part의 중복 게시를 유일성 제약과 멱등성 키로 차단한다.
  - 같은 Manifest 안에서 동일 shard의 관측 기간이 겹치지 않는다는 조건은 PostgreSQL exclusion constraint 또는 게시 트랜잭션 검증으로 강제한다.

### DMD-017 — 초기 PostgreSQL 물리 파티션 미도입

- 상태: 현재 초안 확정, production 부하 검증과 운영 임계값 필요
- 사용자 선택: 질문 12의 `D`
- 결정:
  - 초기 PostgreSQL 스키마에는 선언적 RANGE, LIST 또는 HASH 물리 파티션 테이블을 만들지 않는다.
  - 봇 사건, 주문, 체결, 원장과 감사·Outbox 같은 append-only 테이블은 단일 논리 테이블과 실제 조회 패턴에 맞는 복합 B-tree 또는 필요한 경우 BRIN 인덱스로 시작한다.
  - 구성·기준·상태 테이블에도 선제 물리 파티션을 적용하지 않는다.
  - 도메인 `bot.bot_partitions`는 봇의 예산·전략 소유 경계이며 PostgreSQL 물리 파티션과 무관하다.
- 미래 호환성:
  - 대용량 후보 테이블에는 `bot_id`, `occurred_at` 또는 `created_at`, 봇 사건 순번과 명시적 기본 키를 유지하여 향후 hash 또는 range 전환 경로를 열어 둔다.
  - 애플리케이션 쿼리는 물리 자식 테이블 이름에 의존하지 않고 논리 테이블과 안정된 인덱스 키만 사용한다.
  - 보존·삭제는 아직 확정되지 않은 정책에 따라 수행하며 대량 삭제 비용이 확인되면 시간 파티션 도입을 재평가한다.
- production 재검증:
  - 예상 최대 봇 수, 사건·주문·체결 증가율, 보존 기간, 핵심 조회 p95/p99, 인덱스 크기, vacuum 시간, bloat, 복제 지연과 백업·복원 시간을 부하 시험으로 측정한다.
  - 단일 테이블이 메모리·vacuum·보존·복구 목표를 충족하지 못하면 `bot_id` hash, 시간 range 또는 용도별 혼합 파티션 마이그레이션을 별도 설계한다.
  - 전환은 shadow table, dual verification, backfill, 검증된 cutover와 rollback 계획을 갖추고 수행한다.
  - 이 부하·운영 검증 전에는 물리 파티션 미도입만으로 production-ready가 입증됐다고 표현하지 않는다.

### DMD-018 — 현재 성과 Projection과 공식 스냅샷

- 상태: 확정
- 사용자 선택: 질문 13의 `A`
- 결정:
  - PostgreSQL의 현재 성과 Projection은 커밋된 공식 원장·포지션 사건을 원천으로 멱등 갱신한다.
  - 현재 Projection은 마지막으로 반영한 `bot_event_sequence`와 계산 규칙 버전을 기록하여 지연·중복·재구축 여부를 판별할 수 있게 한다.
  - 불변 공식 성과 스냅샷은 ET 거래일 종료, 방 평가 시작·종료, 봇 중단과 리더보드 산정 기준 시점에 생성한다.
  - 거래가 없는 임의 시간마다 빈 스냅샷을 만들거나 모든 사건마다 불변 스냅샷을 생성하지 않는다.
  - 긴 성과 시계열과 계산 상세는 주 단위 S3 Parquet 객체로 저장하고 PostgreSQL은 현재값, 경계 스냅샷과 객체 매니페스트를 소유한다.
  - NoSQL은 봇 운영 화면과 현재 리더보드의 재생성 가능한 조회 복제본만 소유한다.
- 예정 DBML 반영:
  - `performance.bot_current_projections`에 봇별 현재 지표 문서, 원장·포지션 해시, 마지막 사건 순번, 계산 규칙 버전과 갱신 시각을 둔다.
  - `performance.bot_snapshots`에 스냅샷 종류, 기준 사건 순번, 평가 시각, 불변 지표 문서, 입력 해시와 계산 규칙 버전을 둔다.
  - 같은 봇·스냅샷 종류·기준 사건 순번의 중복 생성을 유일성 제약과 멱등성 키로 차단한다.
  - `performance.series_manifests`가 주 단위 Parquet 객체, 기간, 스키마·계산 버전, 내용 해시와 supersession 계보를 연결한다.
  - 리더보드 항목은 정확한 불변 성과 스냅샷을 참조하고 현재 NoSQL Projection을 공식 점수 근거로 사용하지 않는다.

### DMD-023 — 건강 이상 중 안전한 실행 차단과 자동 복구

- 상태: 확정된 DBML 재설계 입력, 제품 정본 조정 전 제안

### DMD-029 — 봇 보관·논리 삭제와 메타데이터 동시성

- 상태: 확정된 DBML 재설계 입력, 제품 정본 조정 전 제안
- 사용자 선택: 2026-07-27 직접 보정
- 결정:
  - `archived_at`은 `STOPPED` 봇을 일반 목록에서 되돌릴 수 있게 숨기는 보관 표시다.
  - `deleted_at`은 사용자 관점에서 되돌릴 수 없는 논리 삭제 표시다. 보관 후 삭제와 보관을 거치지 않는 즉시 삭제를 모두 허용한다.
  - `RUNNING` 또는 `STOPPING` 봇의 삭제 요청은 즉시 `deleted_at`을 기록하지 않는다. 기존의 멱등적인 중단 요청으로 미체결 주문 취소와 정산을 마치고 `STOPPED`가 된 뒤 삭제를 확정한다.
  - 삭제된 봇은 일반·보관 목록과 신규 운영 대상에서 제외한다. 물리 제거는 별도 보존 기간·법적 보존 정책을 통과한 뒤 수행하며 공식 주문, 체결, 원장, 사건과 감사 증거를 연쇄 삭제하지 않는다.
  - 봇의 수정 가능한 필드는 `edit_sequence`를 사용한다. 이 값은 표시 버전이나 복사 계보가 아니라 낙관적 동시성 번호다.
  - `edit_sequence`는 0에서 시작하며 이름, 보관, 보관 해제 또는 삭제 같은 수정이 성공할 때마다 정확히 1 증가한다. 클라이언트가 제출한 예상 값이 현재 값과 다르면 갱신을 거절한다.
- DBML 반영:
  - `bot.bots`에 nullable `deleted_at`, `edit_sequence`, `updated_at`을 둔다.
  - 활성 목록은 `deleted_at IS NULL AND archived_at IS NULL` 조건을 사용하고 운영 마이그레이션에서 이 조건의 부분 인덱스를 생성한다.
  - 삭제 요청·중단 완료·논리 삭제 확정은 감사 또는 공식 사건으로 남기며 재시도에도 같은 결과가 나도록 멱등 처리한다.

### DMD-030 — 흐름 UI 레이아웃 영속화와 실행 의미 분리

- 상태: 확정된 DBML 재설계 입력, 제품 정본 조정 전 제안
- 사용자 선택: 2026-07-28 직접 보정. 2026-07-27의 레이아웃 비영속화 결정을 대체한다.
- 결정:
  - 흐름 요소의 좌표·크기, 그룹 배치·접힘, 선택 상태, edge routing hint, viewport와 zoom을 PostgreSQL의 `layout_document JSONB`에 저장해 사용자가 편집한 그래프 화면을 그대로 복원한다.
  - `layout_document`의 요소·엣지 키는 `semantic_document`의 안정 식별자를 참조해야 하며, 존재하지 않는 키·중복 키·유효하지 않은 수치와 지원하지 않는 레이아웃 스키마는 저장 검증에서 거절한다.
  - 편집 중 `bot_workspaces.workspace_document`도 각 전략의 `semanticDocument`와 `layoutDocument`를 분리해 포함한다. 완성된 흐름에는 모든 의미 요소의 유효한 레이아웃이 있어야 하며 dangling layout 참조는 허용하지 않는다.
  - 실행 의미는 안정적인 요소 식별자, 타입 지정 포트, 연결, 매개변수, 의미 그룹과 `RISK_POLICY`를 포함하는 `semantic_document`만 소유한다.
  - 레이아웃은 별도 `layout_hash`로 무결성을 확인하고 `semantic_hash`, `configuration_hash`, 실행 계획, 의미 검증과 백테스트 결과에는 영향을 주지 않는다.
  - 자동 배치는 새 흐름이나 레이아웃이 없는 과거 데이터를 위한 초기값 생성·복구 수단으로만 사용하며, 저장된 사용자 레이아웃을 임의로 덮어쓰지 않는다.
  - 플랫폼 템플릿은 의미 골격만 제공할 수 있으며, 인스턴스 생성 시 자동 배치한 레이아웃을 새 흐름의 `layout_document`에 저장한다.
  - 봇 캔버스에서 파티션과 전략 카드의 `position_x`, `position_y`는 사용자가 수정 가능하다고 별도로 확정한 aggregate 메타데이터이므로 유지한다.
  - 봇, 파티션과 전략의 수정 가능한 필드 동시성 컬럼은 모두 `edit_sequence`, 갱신 시각은 `updated_at`으로 통일한다.
- DBML 반영:
  - `bot.strategies`에 `layout_document`, `layout_schema_version`과 `layout_hash`를 둔다.
  - `bot.strategies.configuration_hash`는 `block_catalog_version_id`와 `semantic_hash`의 규정된 정규 표현만 결합한다.
  - 레이아웃 갱신도 `bot.strategies.edit_sequence`를 증가시키고 `updated_at`을 변경한다.

## 범위 축소 감사

사용자의 요청에 따라 프로젝트에서 참여 방식이나 별도 실행 이력을 명시하지 않은 선제 설계와 중복 조회 구조를 DBML에서 제거했다. 핵심 제품 기능과 공식 무결성에 필요한 테이블은 개수가 많더라도 유지한다.

| 제거 요소 | 제거 이유 | 제거로 발생하는 문제 또는 제한 |
| --- | --- | --- |
| `identity.accounts.public_id` | 별도의 외부 공개 식별자 정책이 프로젝트에 없음 | API에서 내부 UUID를 그대로 노출하지 않으려면 이후 공개 ID 정책과 컬럼을 추가해야 함 |
| `storage.object_links` | 각 도메인이 이미 객체를 명시적 FK로 연결하며 범용 다형성 링크 요구가 없음 | 새 도메인이 S3 객체를 연결할 때 전용 FK 또는 매니페스트를 추가해야 함 |
| `storage.integrity_checks` | 개별 무결성 검사 실행 이력 요구가 없음 | 현재 객체의 `verified_at`만 남으므로 과거 검사 시도와 실패 이력을 별도 조회할 수 없음 |
| `market_data.provider_agreements` | 정확한 공급자·계약·권리 구조가 외부 검증 미결정 상태임 | 여러 계약 버전과 저장·백테스트·재배포 권리를 행 단위로 관리할 수 없음. 공급자 선정 시 다시 설계해야 함 |
| `bot.bot_universe_bindings`, `bot.strategy_universes`, `market_data.official_universes` 계열 | 현재 제품은 개별 종목 선택만 지원하며 Universe 동작과 시점별 구성 규칙이 미확정임 | 향후 Universe 기능을 도입할 때 고정·동적 구성 의미, 버전 핀, 백테스트 재현성과 마이그레이션을 함께 새로 설계해야 함 |
| `trading.ledger_account_balance_projections` | 별도 잔액 Projection 요구가 없고 원장 항목에서 계산 가능함 | 봇 운영 개요의 잔액 조회가 커지면 집계 비용이 증가할 수 있으며, 규모가 입증되면 재생성 가능한 Projection을 추가해야 함 |
| `backtest.performance_metrics` | `performance_summaries.summary_document`와 같은 지표를 중복 정규화함 | 지표별 SQL 필터·정렬은 JSONB 인덱스 또는 후속 읽기 모델이 필요함 |
| `performance.calculation_runs` | 성과 계산 작업 자체의 독립 실행 이력 요구가 없음 | 성과 계산 재시도·작업 실패 이력을 별도 화면에서 추적할 수 없고 스냅샷 결과와 운영 로그로만 확인함 |
| `performance.bot_metric_values` | `bot_snapshots.metrics_document`와 중복됨 | 개별 지표의 강한 컬럼 타입과 FK 수준 제약이 줄어듦 |
| `competition.leaderboard_calculation_runs` | 리더보드 계산 작업의 별도 실행 이력 요구가 없음 | 계산 재시도·중간 실패 분석은 공식 스냅샷과 운영 로그에 의존함 |

이 제거는 기능을 영구 금지하는 결정이 아니다. 실제 요구나 규모가 확인되면 근거와 함께 다시 추가한다.

감사 중 `competition.room_access_codes`를 미결정 요소로 판단해 제거했으나, 제품 문서에서 초대 링크와 초대 코드를 모두 제공한다는 직접 근거를 확인했다. 코드 전용 구조를 복원하지 않고 두 방식을 함께 표현하는 `competition.room_invitations`로 바로잡았다.

## 다음 사용자 선택이 필요한 항목

봇 스키마 재검토 질문을 진행 중이다. 아래 외부 근거 항목은 임의 확정하지 않고 버전·실패 차단 구조만 초안에 반영한다.

## 외부 근거가 필요한 미결정 항목

다음 항목은 사용자 A/B/C 선택으로 임의 확정하지 않는다.

- 금액·가격·수량·수수료·담보·손익의 정확한 정밀도와 반올림
- 기업행사별 회계 처리와 원장 정정 방식
- 시장·호가·대차·기업행사 공급자, 라이선스와 저장·재배포 권리
- 공식 성과 지표와 방 점수 공식
- 개인정보·공식 원장·감사·시장 데이터·객체의 보존 및 삭제 기간
- 가용성, 지연, 처리량, 백업·복원과 재해 복구 목표
- 전략 블록·지표·공식 카탈로그의 정확한 목록과 실행 자원 상한

이 항목은 버전 식별자와 실패 차단 구조만 DBML에 준비하고, 근거가 확정되기 전에는 낙관적인 기본값으로 대체하지 않는다.
