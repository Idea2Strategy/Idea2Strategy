# Competition backtesting redesign decisions

상태: 확정된 사용자 결정을 정규화한 격리 제안. 제품 정본 승인 또는 운영 마이그레이션이 아니다.

## 확정된 결정

### 1. 공통 Competition 루트

- 사용자 선택: A
- 기존 사용자 생성 대회와 플랫폼 공식 대회는 `competition.rooms`를 공통 루트로 사용한다.
- 대회 실행 유형은 `LIVE_PAPER`, `BACKTEST`로 구분한다.
- 주최자 유형은 `PLATFORM`, `USER`로 구분한다.
- 참가, 일정, 규칙, 사건, 리더보드의 공통 구조는 공유하고 실행 유형별 설정만 분리한다.
- 플랫폼 공식 대회는 사용자 계정을 소유자로 가장하지 않는다. 실제 개설 작업자는 운영 감사 관계로 별도 기록한다.

### 2. 평가 시작 전 Bot 실행 게이트

- 사용자 선택: A
- `bot.bots`에 `execution_eligible_from`을 추가하고 개인 Bot은 즉시, 평가 전에 생성된 대회 참가 Bot은 해당 대회의 `evaluation_starts_at`부터 실행 가능하게 한다. 이미 평가 중인 공식 백테스팅 대회 참가 Bot은 생성·입력 잠금 완료 시점부터 백테스트 평가가 가능하다.
- `waiting`, `paused`, `scheduled` 같은 Bot 수명주기 상태는 추가하지 않는다.
- 평가 Worker는 `lifecycle_status = RUNNING`만으로 실행하지 않고 `now() >= execution_eligible_from`도 함께 확인한다.
- 대회 참가 생성 시 `execution_eligible_from`은 잠긴 Room 일정에서 복사하며 이후 일정 변경으로 소급 변경하지 않는다.
- 기존 `started_at`은 실제 실행 시작 시각으로 nullable하게 바꾸고, 평가 시작 전에는 null로 둔다.
- LIVE_PAPER와 BACKTEST가 평가 시작 이후 어떤 실행기를 사용하는지는 Competition 실행 유형으로 라우팅하며 다음 결정에서 구체화한다.

### 3. 공식 백테스팅 대회의 비공개 다중 기간 평가

- 사용자 선택: B를 다중 기간 평가로 구체화.
- 공식 백테스팅 대회는 하나의 기간만 사용하지 않고 플랫폼이 사전에 잠근 여러 평가 기간을 모든 참가 Bot에 동일하게 적용한다.
- 정확한 평가 날짜와 선택된 데이터셋·Manifest 목록은 참가 및 평가 중에 공개하지 않는다.
- 각 기간의 결과를 결합한 평균 성과로 최종 평가한다. 기간별 상태 초기화와 평균 가중 방식은 후속 결정에서 확정한다.
- 평가 기간별 매수, 매도, 판단 결과와 상세 재생 증거는 대회가 `ENDED`가 되기 전에는 사용자에게 제공하지 않는다.
- 상세 결과는 S3 불변 객체에 저장하고 PostgreSQL은 기간 묶음, 실행, 공개 시각, 해시와 객체 매니페스트를 관리하는 방향으로 설계한다.
- 대회 종료 후 상세 결과는 아래 공개 범위 결정에 따라 참가 Bot 소유자에게만 제공한다.

### 4. 종료 후 상세 결과 공개 범위

- 사용자 선택: A
- 대회가 `ENDED`가 된 뒤 참가자는 자신이 소유한 참가 Bot의 기간별 매수·매도·판단 결과와 재생 증거만 조회할 수 있다.
- 다른 참가 Bot에 대해서는 허용된 최종 점수, 순위와 공개 요약만 제공하고 거래·판단 상세는 제공하지 않는다.
- 대회 참가 여부와 관계없이 다른 계정의 비공개 Strategy 또는 상세 실행 증거를 조회할 수 없다.
- 운영자는 부정행위·장애 조사에 필요한 별도 감사 권한으로 접근하며, 사용자 공개 권한과 분리하고 감사 사건을 남긴다.

### 5. 평가 기간 중요도 가중치

- 공식 백테스팅 대회의 생성 주체인 플랫폼이 각 비공개 평가 기간의 중요도를 직접 판단하여 가중 비율을 설정한다.
- 기간 가중치는 양수이며 전체 합계가 정확히 1이 되도록 강제한다.
- 가중치, 기간 집합, 채점 규칙과 계산 버전은 참가 접수 전에 하나의 불변 평가 계획으로 잠그고 평가 도중 변경하지 않는다.
- 기간 길이나 거래일 수로 자동 가중하지 않는다. 짧더라도 중요한 시장 국면이면 플랫폼이 더 높은 중요도를 부여할 수 있다.
- 기간별 결과를 0~100점으로 먼저 변환하지 않는다.
- 동일한 성과 지표별로 기간 중요도 가중치를 적용한다. 예를 들어 가중 수익률은 각 기간 수익률에 기간 가중치를 곱해 합산한다.
- 여러 성과 지표를 최종 순위 공식으로 결합할 때의 계수와 방향은 잠긴 `scoring_template_version`이 소유한다.
- 일관성·하방 위험을 별도 페널티로 적용할지는 후속 결정에서 확정한다.

### 6. 평가 기간별 독립 초기 상태

- 사용자 선택: A
- 각 비공개 평가 기간은 서로 완전히 독립적으로 실행한다.
- 모든 기간은 대회 규칙에 잠긴 동일한 초기 자금에서 시작한다.
- 기간 시작 시 보유 포지션, 미체결 주문, Buying Power 예약, 원장 잔액 변동과 Flow 런타임 상태를 모두 초기화한다.
- 앞 기간의 현금·포지션·Flow 상태를 다음 기간으로 넘기지 않는다.
- 동일한 참가 Bot 구성 해시를 각 기간에 재사용하되 입력 데이터셋, 기간과 실행 결과는 기간별로 독립 고정한다.

### 7. 기간별 Backtest Run과 Competition 연결

- 사용자 선택: A
- 참가 Bot 하나에는 평가 계획에 포함된 기간 수만큼 독립적인 `backtest.runs`를 생성한다.
- 일반 백테스트 실행·시도·입력 잠금·요약·S3 상세 매니페스트 구조를 그대로 재사용한다.
- `competition.backtest_evaluation_plans`는 공식 백테스팅 대회의 잠긴 평가 계획과 전체 해시를 소유한다.
- `competition.backtest_evaluation_periods`는 비공개 평가 기간, 중요도 가중치, 입력 데이터셋 묶음과 기간 순서를 소유한다.
- `competition.backtest_period_runs`는 Participation·평가 기간·Backtest Run을 1:1 실행 단위로 연결한다.
- `(participation_id, evaluation_period_id)`와 `run_id`를 각각 UNIQUE로 강제하여 같은 참가 Bot·기간의 중복 실행과 하나의 Run 재사용을 막는다.
- `competition.backtest_aggregate_results`는 모든 필수 기간 Run이 성공·검증된 뒤 기간 가중치를 적용한 최종 집계 결과와 계산 해시를 저장한다.
- 특정 기간 실행 실패는 해당 Run의 시도로만 재시도하고 다른 성공 기간의 잠긴 결과를 다시 계산하지 않는다.

### 8. 평가 중 최종 점수 공개

- 사용자 선택: C를 제한 공개 방식으로 구체화.
- 대회가 진행 중이어도 참가 Bot의 모든 비공개 기간 평가가 완료되고 집계 결과가 검증되면 해당 평가의 가중 최종 점수를 공개한다.
- 개별 평가 기간의 점수, 기간별 성과 지표, 기간 날짜, 데이터셋과 매수·매도·판단 상세는 공개하지 않는다.
- 일부 기간만 성공한 부분 집계값, 실패한 실행의 임시 점수와 재시도 과정의 점수는 공개하지 않는다.
- 동일한 공식 평가의 재시도는 새 공개 점수로 취급하지 않고 검증된 하나의 aggregate result만 공개한다.
- 사용자 선택에 따라 최종 점수가 공개되는 즉시 현재 리더보드 순위도 다시 계산해 공개한다.
- 순위에 `임시` 표시는 붙이지 않는다. 이후 다른 참가 Bot의 검증된 최종 점수가 공개되면 기존 순위는 자연스럽게 변경될 수 있다.
- 아직 전체 기간 평가가 끝나지 않은 Bot은 점수와 순위 계산 대상에서 제외한다.
- 공식 백테스팅 대회는 평가 중 신규 참가가 가능하므로 늦게 참가하는 사용자가 이미 공개된 최종 점수와 현재 순위를 볼 수 있다는 점을 허용 정책에 반영해야 한다.

### 9. 평가 시작 전 참가 취소와 Strategy 변경

- 사용자 선택: A
- 참가자는 `evaluation_starts_at` 전까지만 자신이 등록한 특정 Participation을 취소할 수 있다.
- 취소는 Participation 행을 삭제하지 않고 상태와 append-only Participation Event로 보존한다.
- 취소된 Participation이 소유한 실행 전 Bot은 물리 삭제하지 않고 `deleted_at`을 설정해 논리 삭제한다.
- 취소 완료 트랜잭션에서 해당 계정의 `per_account_bot_limit` 점유와 방 전체 참가 슬롯을 반환한다.
- Strategy 변경은 기존 Participation의 `bot_id`나 Bot 실행 의미를 수정하지 않는다. 기존 참가를 취소한 뒤 선택한 Strategy 상태로 독립 새 Bot·Participation을 원자적으로 생성한다.
- 라이브 대회는 평가 시작 이후 참가 취소, Strategy 변경, Bot 교체와 신규 참가를 모두 금지한다.
- 공식 백테스팅 대회는 평가 진행 중 신규 참가를 허용하되, 정확한 참가 마감 시각과 생성 후 취소·교체 가능 범위는 별도로 결정한다.

### 10. 기간 평가 기술 실패 처리

- 사용자 선택: A
- 적용 대상은 공식 `BACKTEST` 대회다.
- 음수 수익률, 체결 0건, 조건 미충족과 큰 손실은 유효한 평가 결과이며 기술 실패가 아니다.
- 참가 Bot은 잠긴 모든 평가 기간의 결과가 성공하고 해시 검증을 통과해야 최종 집계 점수와 순위를 받는다.
- 재시도 후에도 Bot 고유의 결정적 계산 오류로 한 기간의 결과를 만들 수 없으면 해당 Participation을 `EVALUATION_FAILED`로 종료하고 점수·순위에서 제외한다.
- 공통 시장 데이터 손상, 공유 입력 누락 또는 평가 인프라 장애는 참가 Bot 고유 실패로 처리하지 않고 동일 입력으로 재시도한다.
- 공통 원인을 복구할 수 없어 동일 조건 평가가 불가능할 때만 Room 전체를 `INVALIDATED`로 전환한다.
- 성공한 일부 기간만 사용해 가중치를 재정규화하거나 부분 점수를 만들지 않는다.

### 11. 공식 백테스팅 대회의 진행 중 참가 마감

- 사용자 선택: A
- 공식 백테스팅 대회 일정에 `participation_closes_at`을 두고 해당 시각 전까지만 진행 중 신규 참가를 허용한다.
- 논리적 기본값은 같은 일정의 `evaluation_ends_at`이다. 대회 생성자는 필요하면 더 이른 시각을 명시할 수 있다.
- PostgreSQL 컬럼 DEFAULT는 같은 행의 `evaluation_ends_at`을 직접 참조할 수 없으므로 생성 서비스 또는 `BEFORE INSERT` trigger가 미입력 값을 복사한다.
- `participation_closes_at <= evaluation_ends_at`을 DB CHECK로 강제한다.
- 라이브 대회는 별도 유형 규칙으로 `participation_closes_at <= evaluation_starts_at`을 강제하고 평가 시작 뒤 참가를 금지한다.
- 마감과 동시에 신규 참가 슬롯 예약을 차단하되 마감 전에 원자적으로 승인된 Participation은 보존한다.
- 사용자 선택에 따라 참가 마감 전에 승인된 Bot은 `evaluation_ends_at`이 지나도 모든 기간 평가와 검증을 끝까지 진행한다.
- `evaluation_ends_at`은 신규 평가 접수의 기본 마감 기준이지 이미 승인된 Run을 강제 중단하는 시각이 아니다.
- 모든 승인된 Participation이 성공 또는 최종 실패 상태가 될 때까지 Room은 `EVALUATING`을 유지하고 별도의 waiting 상태를 추가하지 않는다.
- 모든 Participation이 terminal 상태가 된 뒤 최종 리더보드 스냅샷을 확정하고 Room을 `ENDED`로 전환하며 실제 완료 시각을 `ended_at`에 기록한다.

### 12. 평가 완료 최종 제한 시각

- 사용자 선택: A
- 공식 백테스팅 대회 일정에 `finalization_deadline_at`을 추가하고 `finalization_deadline_at >= evaluation_ends_at`을 강제한다.
- 대회 생성 시 플랫폼이 참가 규모, 기간 수와 처리 성능에 맞는 유예 시간을 명시적으로 설정하고 평가 도중 변경하지 않는다.
- 최종 제한 시각까지도 끝나지 않은 Bot 고유 평가 오류는 해당 Participation을 `EVALUATION_FAILED`로 종결한다.
- 공통 데이터셋·공유 입력·플랫폼 장애 때문에 동일 조건 평가를 완료할 수 없으면 Room 전체를 `INVALIDATED`로 종결한다.
- terminal 처리, 실패 원인과 운영 판단은 Room Event·Participation Event와 감사 기록으로 남긴다.

### 13. 진행 중 참가 승인 후 취소 금지

- 사용자 선택: B
- 적용 대상은 이미 `EVALUATING` 중인 플랫폼 공식 백테스팅 대회다.
- Bot·Participation·기간별 Run·입력 잠금 생성 트랜잭션이 커밋되어 참가가 승인되면 첫 Run 시작 전이라도 사용자 취소를 허용하지 않는다.
- 승인 후 Strategy 교체나 Participation의 `bot_id` 변경도 허용하지 않는다.
- 사용자가 다른 Strategy를 평가하려면 남은 `per_account_bot_limit` 안에서 독립 새 Bot으로 추가 참가해야 한다.
- 플랫폼 원인으로 참가 생성 트랜잭션이 완성되지 않은 경우에는 승인된 참가로 취급하지 않고 전체를 롤백한다.

### 14. 계정별 참가 Bot 한도 점유

- 사용자 선택: A
- 플랫폼 공식 백테스팅 대회가 진행 중일 때 승인된 모든 Participation은 평가 성공, `EVALUATION_FAILED` 또는 점수 미생성과 관계없이 대회 종료까지 계정의 `per_account_bot_limit` 한 슬롯을 계속 점유한다.
- 평가 실패를 이용해 새 Strategy를 반복 시험하거나 백테스트 계산 자원을 우회 소비할 수 없게 한다.
- 대회 평가 시작 전에 정상 취소된 Participation만 기존 결정에 따라 슬롯을 반환한다.
- 참가 생성 트랜잭션이 롤백되어 승인 자체가 성립하지 않은 요청은 슬롯을 점유하지 않는다.
- 계정별 한도 검사는 Room 행 또는 별도 한도 카운터를 잠근 트랜잭션에서 수행하여 동시 요청이 한도를 초과하지 못하게 한다.

### 15. 가중 위험 지표와 최악 기간 위험

- 사용자 선택: A
- 적용 대상은 플랫폼 공식 백테스팅 대회의 최종 점수 계산이다.
- 기간별 결과를 0~100점으로 변환하지 않고 원래 성과 지표를 유지한다.
- `weighted_max_drawdown`은 각 기간의 최대 낙폭에 잠긴 기간 중요도를 적용해 계산한다.
- `worst_period_max_drawdown`은 모든 필수 평가 기간 중 가장 큰 손실의 최대 낙폭을 별도로 보존한다.
- 두 지표는 서로를 대체하지 않으며 `scoring_template_version`이 대회별 반영 계수와 방향을 잠근다.
- `backtest_aggregate_results`는 가중 성과 지표, 최악 기간 지표, 사용한 기간 결과 해시 집합과 계산 규칙 버전을 함께 저장한다.

### 16. 비공개 평가 기간의 비중복

- 사용자 선택: A
- 공식 백테스팅 평가 계획에는 최소 2개의 평가 기간이 있어야 한다.
- 같은 평가 계획의 기간들은 날짜 또는 거래 세션 범위가 서로 겹칠 수 없다.
- 중요한 시장 구간은 다른 기간 안에 중복 삽입하지 않고 해당 기간의 명시적 중요도 가중치를 높여 반영한다.
- PostgreSQL exclusion constraint 또는 잠금된 생성 함수가 같은 평가 계획의 `[evaluation_start, evaluation_end]` 범위 중복을 차단한다.
- 기간 집합, 기간 가중치 합계와 비중복 검증이 모두 성공한 뒤에만 평가 계획을 잠글 수 있다.

### 17. 평가 규칙과 비공개 계획의 단계별 공개

- 다음 항목은 플랫폼 공식 백테스팅 대회의 모집, 평가와 종료 상태에 관계없이 항상 공개한다.
  - 초기 자금
  - 수수료 정책과 버전
  - 고정 슬리피지 정책과 버전
  - 채점 공식
  - 계산 규칙 버전
- 다음 비공개 평가 계획 정보는 Room이 `ENDED`가 된 뒤 공개한다.
  - 실제 평가 기간 목록
  - 각 기간의 중요도 가중치
  - 사용한 시장 데이터셋·Manifest 식별자, 버전과 내용 해시
  - 전체 평가 계획 문서와 해시
- 시장 데이터 원본 객체는 공급자 권리와 라이선스 정책을 따르며 공개 대상에 포함하지 않는다.
- 평가 계획을 잠근 시점에는 비밀 nonce를 포함한 `evaluation_plan_commitment_hash`만 공개할 수 있다. `ENDED` 뒤 계획과 nonce를 함께 공개하여 평가 중 계획이 바뀌지 않았음을 검증하되 숨은 날짜의 사전 대입 공격을 막는다.
- 참가 Bot별 매수·매도·판단 상세는 평가 계획 공개와 별개로 기존 결정에 따라 해당 Bot 소유자에게만 제공한다.

### 18. 진행 중 공개 점수 확인 후 추가 참가

- 공식 백테스팅 대회 사용자는 이미 공개된 다른 참가 Bot의 최종 점수와 현재 순위를 확인한 뒤에도 `participation_closes_at` 전이고 계정·Room 참가 한도가 남아 있으면 새 Strategy로 추가 참가할 수 있다.
- 기간별 점수, 숨은 기간, 기간 가중치와 상세 실행 증거는 계속 비공개이므로 공개된 정보는 검증된 집계 최종 점수와 현재 순위로 제한한다.
- 진행 중 승인된 Participation은 취소할 수 없고 성공·실패와 관계없이 계정 참가 한도를 계속 점유하므로 반복 시험 제출 횟수는 `per_account_bot_limit`으로 제한한다.

### 19. 최종 집계 공식 소유권

- 기간별 원래 성과 지표에 플랫폼이 잠근 기간 중요도 가중치를 적용한다.
- `weighted_max_drawdown`과 `worst_period_max_drawdown`을 함께 계산한다.
- 모든 대회에 고정된 별도 분산·일관성 페널티를 자동 적용하지 않는다.
- 추가 위험 페널티, 지표별 계수와 최종 결합 공식이 필요하면 항상 공개되는 불변 `scoring_template_version`에 명시한다.

## 사용자에게서 직접 확인된 공통 참가 정책

- 플랫폼 공식 라이브 모의투자 대회와 사용자 생성 라이브 모의투자 대회는 평가 시작 뒤 신규 참가할 수 없다.
- 플랫폼 공식 백테스팅 대회는 평가가 진행 중이어도 신규 참가할 수 있다.
- 한 계정은 하나의 대회에 여러 봇을 참가시킬 수 있다. 허용 개수는 대회 규칙의 `per_account_bot_limit`으로 제한한다.
- 사용자는 기존 봇을 선택해 참가시키지 않는다. 참가할 Strategy를 선택하면 서버가 당시 Strategy 실행 의미를 복사한 독립 새 Bot과 Participation을 한 트랜잭션으로 생성한다.
- 생성된 Bot에는 원본 Strategy 식별자나 복사 출처를 저장하지 않는다.
- 평가 전에 생성된 참가 Bot은 대회 평가 시작 전까지 실행하지 않는다. 이미 평가 중인 공식 백테스팅 대회에 참가한 새 Bot은 생성·입력 잠금이 끝난 뒤 기간별 평가를 시작한다.

## 현재 DBML에서 확인된 영향

- `competition.participations`의 `(room_id, owner_account_id) UNIQUE`는 계정당 여러 Bot 참가를 막으므로 제거해야 한다.
- 계정별 참가 수는 `room_rules.per_account_bot_limit`을 읽고 같은 대회·계정의 활성 Participation 수를 잠금 상태에서 검사해야 한다.
- Bot 생성, Bot 구성 스냅샷 계층, Participation, 최초 사건과 Outbox는 하나의 트랜잭션으로 생성되어야 한다.
- `bot.bots.execution_eligible_from`과 nullable `started_at`으로 별도 대기 상태 없이 평가 시작 전 실행을 차단해야 한다.
